# v0.5.0 roadmap draft

This document records the first direction for `v0.5.0` after the `v0.4.1`
patch release.

Status as of 2026-05-01: `v0.4.1` is released with the chart-source quote
readiness fix. `v0.5.0` should start from the two investment lanes that remain
most useful now that the basic CLI surface is broad enough: Desktop-free
reusable data reads, and Desktop-backed agent operation.

## Goal

`v0.5.0` should make the CLI more useful as an agent-operated TradingView
toolkit, not merely add more commands. The main question is how to make data
and UI-dependent workflows reliable enough for downstream agents without
turning the project into a broad trading bot or generic browser automation
framework.

The preferred direction is:

1. continue Desktop-free reads where the endpoint evidence is strong and the
   result is useful outside the CLI;
2. improve Desktop-backed operations where the visible TradingView app is the
   source of truth, especially target selection, readiness, and diagnostics;
3. document the boundary between `tv` and Computer Use so agents know when to
   use structured CLI reads and when to use visual/manual inspection;
4. avoid broad new mutation surfaces unless they have exact post-checks and a
   clear operator workflow.

## Lane 1: Desktop-free reusable data

This lane treats `tradingview-market`, `tradingview-scanner`, and related
commands as reusable read tools. The aim is to reduce dependence on a live
TradingView Desktop session when the data can be read safely without it.

Current state:

- `tv info <SYMBOL>`, `tv quote <SYMBOL>`, and `tv quotes <SYMBOL>...` work
  without Desktop for symbol metadata and scanner-backed quotes.
- `tv scanner scan`, `tv scanner hotlist`, and `tv scanner metainfo` work
  without Desktop for screening and field discovery.
- `tradingview-market` and `tradingview-scanner` expose typed Rust APIs and
  JSON wrappers.
- Desktop-free historical bars remain a research candidate, not a stable
  command. The only strong evidence so far is an undocumented WebSocket path
  that should be lab-gated if pursued.

Good `v0.5.0` candidates:

- a lab-gated `tv bars <SYMBOL>` prototype with bounded count and explicit
  freshness/entitlement wording;
- stronger typed result models for market/scanner crates if downstream code
  starts consuming them directly;
- small scanner field or metainfo improvements driven by concrete workflows.

Not good default candidates:

- cookie/session import, login automation, or authenticated direct HTTP;
- replacing chart-dependent `tv ohlcv` with a browserless path before
  equivalence is proven;
- adding more scanner fields without an operator need.

## Lane 2: Desktop-backed agent operation

This lane treats TradingView Desktop as the authoritative stateful application
and focuses on making agent operation reliable. It is not a replacement for
Computer Use. Instead, `tv` should provide structured state, target handoff,
readiness checks, and post-checks, while Computer Use remains useful for visual
inspection and one-off manual interaction.

Current state:

- `tv tab list` exposes explicit `target_cli_args` for chart and Screener
  targets.
- `tv status` and CDP connection failures expose endpoint details and
  target-readiness hints so agents can distinguish a missing CDP endpoint from
  target-selection problems.
- `tv state` includes chart readiness metadata for the selected chart target.
- `tv screener open --full-page` can prepare a full-page Screener target.
- `tv ohlcv` failure details include chart-bars readiness diagnostics.
- `tv quote <SYMBOL> --source chart` now waits for requested-symbol chart bars
  and fails rather than returning stale previous-symbol data.
- Runtime skills already describe when scanner reads, chart reads, Screener
  reads, and OHLCV should be interpreted differently.

Good `v0.5.0` candidates:

- a Desktop readiness diagnostics slice that makes target/chart/source
  readiness easier for agents to inspect before operation;
- clearer shared diagnostic payloads for `status`, `tab list`, `state`,
  chart-source quote, and OHLCV failures;
- skill updates that pair `tv` structured reads with Computer Use visual
  confirmation when the CLI cannot establish readiness.

Not good default candidates:

- broad generic UI automation expansion;
- DOM retries that hide missing readiness instead of exposing it;
- new account mutations without exact readback and explicit operator approval.

## First slice recommendation

Start `v0.5.0` with Desktop readiness diagnostics rather than more
Desktop-free data. `v0.4.0` already moved the Desktop-free market-data lane
forward substantially, and `v0.4.1` showed that Desktop-backed commands need
first-class readiness semantics. A focused diagnostics slice will make later
Desktop-backed features safer and reduce downstream agent workarounds.

The first ExecPlan is:

- `docs/plans/tradingview-cli-v0.5-desktop-readiness-diagnostics.md`

The first implementation path is additive payload hardening on existing
commands. A broad `tv diagnose` / `tv readiness` command remains deferred until
the existing `status`, `tab list`, `state`, chart-source quote, and OHLCV
diagnostics prove insufficient in downstream use.

## Deferred by default

- MCP server work;
- trading bots, dashboards, or workflow packs;
- raw TradingView endpoint primitives;
- cookie/session import or export;
- broad non-numeric Screener filter editing;
- generic UI automation beyond compatibility needs;
- public-stable crates.io publication promises.
