# v0.26.0 ordered work items and retained backlog

This document is the durable implementation inventory for `v0.26.0` and the
feature work that should remain visible after that release. It complements
`docs/v0.26-roadmap.md`: the roadmap explains direction, while this document
records dependencies, evidence, acceptance conditions, and stop conditions.

Only the current item should have a full ExecPlan under `docs/plans/`. When an
item becomes active, reread the current code and promote that item into a
self-contained ExecPlan following `.agents/PLANS.md`. Do not copy this file
mechanically: decisions and file locations may have changed after the prior
item was implemented.

## Shared constraints

Each work item is a separate implementation and review unit. Start by checking
the worktree, current roadmap, active plan, relevant modules, and tests. Finish
focused tests before the workspace baseline. Do not carry a failing test,
unresolved contract change, or unrelated diff into the next item.

These items must preserve the existing success and error envelopes, ordered
item semantics, partial-success behavior, source metadata, and mutation
boundaries unless an ExecPlan identifies an unavoidable compatibility change
before implementation. They do not add commands, data sources, automatic
fallback, source mixing, ranking, recommendations, or trading decisions.

Tracked files must not contain raw live output, raw bars, raw live or
account-bearing WebSocket frames, credentials, session identifiers,
account-local identifiers, raw target identifiers, or machine-specific
absolute paths. Minimal synthetic protocol fixtures without market data,
identifiers, credentials, or account-local content are allowed for
deterministic tests. Desktop state-changing smoke tests require explicit user
authority; Desktop-free and clearly non-mutating smokes are preferred.

## Ordered implementation inventory

### R0. Reset current sources

Status: complete.

Purpose: make repository guidance identify `v0.25.0` as the latest release,
`v0.26.0` as current planning, and the broken-pipe work as the active
implementation plan.

Evidence before the reset: contributor guidance named `docs/v0.6-roadmap.md`
as a current source, the continuity ledger described much older work, the
README linked `docs/v0.22-roadmap.md` as latest, and the plan index still
listed completed `v0.25.0` release readiness as current.

Acceptance: `AGENTS.md` and `CLAUDE.md` are identical; current source links
point to this roadmap and work inventory; the continuity ledger is concise and
current; the `v0.25.0` release plan is archived; Rust files are unchanged.

### R1. Handle closed output pipes without panic

Status: complete. ExecPlan:
`docs/plans/tradingview-cli-output-broken-pipe.md`.

Problem addressed: `crates/cli/src/app/output.rs` used `println!` and
`eprintln!` for JSON and JSONL. When a downstream reader exited after the first
line, Rust could panic with a broken-pipe write failure, and JSONL workflows
could continue network polling after no consumer remained.

Acceptance: a closed stdout never prints a panic or backtrace; JSONL runners
stop immediately after stdout closes; successful output interrupted by a
closed consumer exits successfully; closing stderr does not replace an
existing command failure with a panic; normal serialized bytes and command
exit codes remain compatible.

Dependency and stop condition: this item has no transport dependency. If
avoiding panic would require changing JSON envelopes, stop and report the
compatibility issue rather than widening scope.

Implementation evidence: writer-level policy tests, the injected watch loop,
local subprocess tests, focused contracts, clippy with warnings denied, the
workspace suite, and a public-safe watch pipeline smoke are green. An
independent read-only review reported no findings.

### R2. Buffer CDP events and enforce absolute wait deadlines

Status: complete. Completed ExecPlan:
`docs/plans/archives/tradingview-cli-cdp-event-buffering-deadlines.md`.

Before R2, `crates/cdp/src/client.rs` discarded protocol events that arrived
while waiting for a method response, and its method-response and event loops
restarted their timeouts after unrelated messages. That could hide an event
from `quote_data_bounded_read` and let unrelated traffic extend a nominal
timeout.

Implemented scope: `CdpClient` now holds interleaved method events in a FIFO
queue, and `next_event` drains that queue before reading the socket. Each
method-response or event wait uses one `Instant` deadline. The sequential
mutable-client model remains unchanged. The queue is bounded to 1024 events and
8 MiB of encoded event text; an overflow fails explicitly rather than dropping
an event.

Acceptance met: an event received before a method response is returned later in
original order; unrelated messages cannot extend the absolute deadline;
existing method errors and timeout exit codes remain unchanged; quote-data
payloads do not change.

Boundary preserved: R2 introduced neither concurrent CDP method calls nor a
background connection task.

Implementation evidence: bounded FIFO and local WebSocket fixtures prove
event retention, ordering, queue limits, and absolute deadlines. Quote-data
contracts, strict clippy, the workspace suite, and a read-only Desktop smoke
are green. Independent review found no runtime issue; its documentation-drift
finding was corrected before R2 was marked complete.

### R3. Add transport deadlines and reuse HTTP clients

Status: complete. Completed ExecPlan:
`docs/plans/archives/tradingview-cli-transport-deadlines-http-reuse.md`.

Before R3, reqwest configuration had no explicit connect or total request
timeout. CDP and bars WebSocket connection establishment was also outside an
explicit end-to-end deadline, and HTTP call sites constructed clients
repeatedly. R3 now uses configured clients and finite transport deadlines;
independent review is the remaining gate.

Expected scope: define justified connect and total deadlines; configure
clients in the crates that own HTTP; add internal client-taking functions
where a top-level operation performs multiple reads; include CDP and bars
WebSocket handshakes in finite deadlines. Keep `tradingview-core` free of a
reqwest dependency. Do not add retry, backoff, caching, or concurrency.

Acceptance met:
stalled connection, stalled response body, CDP
handshake, bars handshake, and pending send fixtures terminate within
deterministic bounds; timeout maps to the existing timeout error; successful
payloads and request counts remain unchanged; configured public and CDP HTTP
clients reuse keep-alive connections in local fixtures. The actual two-symbol
quote operation now proves one-connection reuse and ordered results; heartbeat
pong timeout retains the bars diagnostic contract; scanner and Pine each have
an effective crate-local timeout test.

Independent review approved the main design, and focused re-review approved
all four corrections with no remaining findings.

Stop condition: timeout values must be justified by deterministic tests and
current command behavior. Do not choose one global value merely for
implementation convenience.

### R4. Verify the bars heartbeat wire format

Status: planned after R3.

Problem: `pong_frame` declares a heartbeat payload length that excludes the
trailing delimiter emitted by the same string. The construction is
internally suspicious, but the correct TradingView wire form is still
unconfirmed.

Expected scope: first add byte-accurate tests for one-digit and multi-digit
heartbeat values, framed and bare ping parsing, and multi-packet order. Use
the common frame helper only if the tests establish that the intended payload
is `~h~{value}`. If evidence instead requires the trailing delimiter, include
it in the declared length. Keep raw live frames out of tracked fixtures.

Acceptance: every fixture's declared length equals its payload byte length;
ordinary bars messages and heartbeat packets preserve parse order; bars
success and failure contracts remain unchanged. An optional longer
Desktop-free smoke may supplement, but not replace, deterministic tests.

Stop condition: if tests do not establish which response form TradingView
accepts, do not guess. Record the uncertainty and leave production behavior
unchanged pending public-safe live evidence.

### R5. Make HTTP error classification consistent

Status: planned after R4.

Problem: similar non-success responses from scanner-backed HTTP endpoints can
currently map to different `ErrorKind` values and exit codes. Downstream
automation therefore cannot reliably distinguish transport failure, timeout,
remote API failure, payload failure, and validation.

Provisional policy to confirm in the ExecPlan: local pre-I/O rejection is
`Validation`; DNS, TCP, TLS, and socket failure is `Connection`; an explicit
deadline is `Timeout`; a received non-success HTTP response or unusable remote
payload is `InternalApiUnavailable`; an internal invariant failure is
`Internal`. Remote HTTP 4xx does not become local validation automatically.

Acceptance: local fixtures for connection refusal, timeout, 429, 500,
malformed JSON, and missing required shape produce the documented error and
exit code across market, scanner, Pine, and CDP HTTP ownership boundaries.
Error details remain public-safe.

Stop condition: list any command whose exit code changes before editing it.
If downstream compatibility makes the provisional policy unsuitable, record
and approve an exception rather than silently retaining drift.

### R6. Add measured bounded concurrency to multi-symbol reads

Status: planned last, after R3 and R5 are stable.

Problem: `quotes`, Desktop-free `compare`, and `events compare` read symbols
sequentially. `quotes` and Desktop-free `compare` also lack the 25-symbol
limit already used by events and watch workflows. The current shape is
predictable but scales poorly.

Expected scope: establish deterministic local baselines for 1, 2, 5, 10, and
25 symbols; add a 25-symbol pre-network validation limit; process symbols with
a fixed maximum of four in flight; preserve each symbol's existing internal
sequence initially; attach `requested_index` and restore input order before
payload shaping. Let `watch compare` inherit quote improvements without
changing its event contract. Do not parallelize chart-backed compare.

Acceptance: the test server observes at most four simultaneous symbol reads;
items remain in input order regardless of completion order; partial success,
all-failed details, source metadata, and first-error behavior remain
deterministic; median local fixture time improves over the sequential
baseline. External network timings are supporting observations only.

Stop condition: if deterministic measurement shows no meaningful benefit or
source behavior becomes less reliable, do not retain concurrency merely
because it was planned. Preserve the measurements and report the result.

## Retained feature backlog

These candidates are not part of the ordered robustness gates and are not
required for the `v0.26.0` release. They remain visible so a hardening-focused
release does not erase product work. After R6, the project manager may promote
one candidate at a time by creating a fresh ExecPlan and updating the roadmap
and expected release scope. Without that explicit decision, proceed to the
`v0.26.0` pre-release audit.

### F1. Event range and source availability

Backlog priority: high. Release membership: not required for `v0.26.0`.

Current `events.v1` and `events_compare.v1` expose symbol-scoped earnings and
dividend-like scanner fundamentals. Investigate bounded date-range requests,
additional event types, and explicit source availability. Do not describe
scanner fields as a complete economic or corporate calendar. A distinct
calendar source requires its own feasibility and source-boundary plan.

### F2. Replay screenshot attachment

Backlog priority: high. Release membership: not required for `v0.26.0`.

Extend `tv replay log` only through an explicit option. Define the output
directory, deterministic filenames, overwrite behavior, cleanup, attachment
status, and per-step source metadata before implementation. Screenshot failure
must remain separate from Replay step failure. Do not turn the workflow into
automatic Replay export.

### F3. Richer Strategy Tester evidence

Backlog priority: medium. Release membership: not required for `v0.26.0`.

Build on `tv screenshot --region strategy` and existing structured strategy,
trade, and equity reads. Improve evidence completeness without deriving
metrics from pixels or presenting visual evidence as structured truth.

### F4. Remaining intraday bars date ranges

Backlog priority: medium to low unless a concrete workflow needs them.
Release membership: not required for `v0.26.0`.

The remaining guarded timeframes are `1`, `3`, `45`, `120`, `180`, and `240`.
Any expansion must reuse the existing Desktop-free bars source, count cap,
range alignment, fetch summary, and coverage semantics. It must not fall back
to selected-chart or Replay sources.

### F5. Screener column reset and cleanup

Backlog priority: medium. Release membership: not required for `v0.26.0`.

Define a reliable source for the default column state and a restore-safe
workflow. Existing column mutations should not claim a reset capability until
the expected default can be verified before and after the operation.

### F6. Safe naming and saving of a new Pine script

Backlog priority: medium to low. Release membership: not required for
`v0.26.0`.

Current Pine save behavior refuses to type into an unverified naming dialog
for a new unsaved script. Revisit only after the dialog target, focus, naming
collision behavior, save confirmation, and recovery path can be verified.

### F7. Broader deferred product changes

Priority: not scheduled.

Stable Replay export, a complete event calendar, automatic historical export
expansion, quote-data fallback, automatic source mixing, daemon or dashboard
operation, binary splitting, MCP server work, ranking, scoring, and buy/sell
recommendations remain outside `v0.26.0` by default.

## Promotion and handback

When promoting an item into an ExecPlan, carry over only its verified current
facts, constraints, user-visible outcome, focused tests, workspace baseline,
and stop condition. The implementation handback should state the behavior
change, affected files, before/after evidence, focused and full validation,
live-smoke status, residual risk, out-of-scope discoveries, and worktree
state. Commit and push behavior follows the user's instruction for that turn;
this inventory does not grant remote-write authority.
