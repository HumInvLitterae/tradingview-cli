# v0.29.0 roadmap

This document records the direction after the `v0.28.0` release.

Status as of 2026-07-17: `v0.28.0` is released from commit `e47ba44`. Planning
has moved to `v0.29.0`. The detailed ordered inventory is
`docs/v0.29-work-items.md`. The current ExecPlan is transport measurement and
failure taxonomy; no retry, reconnect, session, broker, or generalized wait
behavior has been implemented or authorized.

## Theme

`v0.29.0` focuses on Desktop transport resilience and diagnosability.

The release should make transient CDP failures classifiable and, where the
failure occurs before any CDP method is dispatched, safely recoverable under a
single bounded budget. It should also identify real latency waste before
changing command structure. Measurement comes first. The roadmap does not
assume that retries, a shared connection, or a new agent-facing command will be
worth their complexity.

Desktop-free reads, Desktop-backed reads, chart mutations, Pine cloud
operations, Replay operations, and screenshots remain explicit surfaces. The
CLI does not automatically mix sources, rank evidence, recommend trades, or
make trading decisions.

## Transport measurement and failure taxonomy

Priority: highest. Status: active planning slice.

Add typed internal timing and failure-stage evidence for target listing, target
selection, WebSocket connection, method response waits, and event waits. Add a
bounded, ignored, public-safe live probe and deterministic local fixtures. The
probe must classify stale-target detectability through one diagnostic
re-discovery after a failed connection without turning that observation into a
retry or success.

Timing is initially internal/probe evidence. The common success envelope does
not gain metadata in this slice. A small stable failure-stage vocabulary is
added to transport error details through a separately typed public-safe
mapping. Raw targets, URLs, Runtime payloads, account-local metadata, and local
paths remain private.

Current plan:
`docs/plans/tradingview-cli-cdp-transport-measurement.md`.

## Pre-dispatch bounded resilience

Priority: high after measurement evidence. Status: gated candidate.

If deterministic and bounded live evidence justify it, add retry only before a
CDP method can have been dispatched: target-list HTTP, target selection,
WebSocket connection, and one stale-endpoint refresh. Use one absolute budget.
Explicit target selection must never silently switch to another target.

Do not retry `call_method`, re-run an operation sequence after an uncertain
outcome, or create a temporary read-command allowlist. This candidate receives
a new ExecPlan only after the measurement plan is complete and reviewed.

## Connection and evaluation topology audit

Priority: medium. Status: queued investigation.

Inspect Desktop-backed workflows for repeated discovery, connection, and
Runtime evaluation within one invocation. Distinguish intentional multi-target
work from removable duplication. Promote an optimization only when a concrete
round trip is measured, its ownership and error-attribution boundary remains
clear, and before/after evidence supports the change.

Combining JavaScript evaluations is not inherently an improvement. Do not
coalesce expressions when doing so weakens stage attribution, absolute
deadlines, mutation ordering, or post-condition readback.

## Recovery-semantics inventory

Priority: medium after failure taxonomy. Status: queued investigation.

Inventory real failures by execution stage and determine what recovery action,
if any, is safe. Retryability is failure-specific; it is not a static command
property. The inventory may propose a closed machine-readable recovery
vocabulary, but no public enum is fixed before the inventory and contract
review.

Method-post-dispatch operation restart remains excluded from the committed
v0.29 core. Any later read restart needs a separate plan proving that the
operation sequence is repeat-safe after an uncertain connection failure.

## Gated shared-connection feasibility

Priority: future candidate. Status: deferred behind measurement and policy
review.

After transport hardening and topology evidence, compare a foreground bounded
session, an explicitly started bounded-lifetime broker, and dropping both. A
broker is a background service and requires an explicit change to the current
daemon exclusion; a TTL does not remove that architectural fact.

Any future design must expose direct, broker-required, or broker-auto ownership
rather than silently changing transports. The gate must consider stale-target
detectability, event-subscription value, latency saved, IPC security, lifecycle,
version skew, per-target serialization, and Windows named-pipe feasibility.

## Autonomous-operation candidates

Priority: future candidates. Status: not committed to v0.29.

Retain bounded named waits and operation-specific input preconditions as
separate candidates. A wait surface must use a closed condition set and one
absolute timeout; it must not accept arbitrary JavaScript. Input checks must
follow the ownership model of each operation rather than imposing one generic
focus rule on all keyboard and pointer paths.

Public recovery metadata, generalized waits, input-precondition expansion, and
standardized post-condition orchestration each require their own ExecPlan and
contract review.

## Retained backlog and exclusions

Retain event date ranges and source availability, Replay screenshot attachment,
remaining intraday bars ranges, Screener column reset, safe new Pine script
naming and save, a complete calendar source, and explicit Replay or historical
export expansion.

Indicator dialog search and exact search-result add remain deferred. The
preserved local prototype must not be applied, dropped, or treated as shipped
without explicit owner direction and fresh current-build feasibility evidence.

Finite-`f64` selected-chart right-offset restoration, width-derived drawing
geometry, and Windows MSIX package-identity launch remain feasibility
candidates, not implied v0.29 work.

Alert and watchlist mutations need separate destructive-operation, security,
post-check, and recovery contracts. MCP server work, an unbounded or
auto-spawned daemon, binary splitting, cookie/session import, login automation,
trading bots, automatic source mixing, ranking, scoring, recommendation, and
buy/sell output remain excluded by default.

## Quality gates

Every implementation slice requires focused deterministic tests, the full Rust
baseline, public hygiene, contributor-guide parity, and documentation/skill
updates when user or agent workflows change. Live probes are opt-in and report
only aggregate public-safe evidence. Live variability supplements but does not
replace deterministic fault-injection acceptance.
