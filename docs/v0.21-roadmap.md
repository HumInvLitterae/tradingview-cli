# v0.21.0 roadmap draft

This document records the `v0.21.0` direction after the `v0.20.0` release.

Status as of 2026-05-26: `v0.20.0` is treated as released. `tv bars
--from/--to` supports daily, weekly, and monthly historical range reads through
the Desktop-free `bars.v1` source. The next useful step is to mature the same
surface for larger ranges and intraday range readiness without adding a new
source or hidden fallback.

## Theme

`v0.21.0` is about historical bars range scale and intraday readiness.

The goal is not to add automatic exports from selected charts, Replay
extraction, realtime feeds, watch loops, source mixing, ranking, or trading
recommendations. The goal is to make `tv bars --from --to` more capable and
more predictable when a requested historical range is too large for one
bounded request or when the requested timeframe is intraday.

Large-range batching / pagination and intraday date-range reads are related
parts of the same problem: users want a bounded, reproducible historical bars
read for a requested symbol, timeframe, and calendar range. They should share
coverage semantics, availability diagnostics, and source-boundary language.
They do not all need to land in the first implementation slice.

## Lane 1: Range scale foundation

Status: complete for the `range_fetch_summary` and large-range cap slices.

`tv bars --from/--to --timeframe 5|15|30|60|1D|1W|1M` is now the historical bars
entry point for the supported date-range timeframes. The range-scale concern
is that a longer daily range, or a high-volume intraday range, can need more
than one bounded fetch.

This lane should define how `tv bars` handles:

- multiple bounded fetch windows inside one requested range;
- deduplication and ascending time order across windows;
- range truncation when a safety cap is reached;
- partial coverage when the source stops returning older bars;
- source availability when the range cannot be satisfied.

The implementation must stay inside the Desktop-free `tradingview_bars_ws`
source. It should not use `tv range`, `tv ohlcv`, Replay, screenshots,
selected-chart state, observe/stream JSONL events, scanner quote, chart quote,
or quote-data as hidden source paths.

First implementation progress: `range_fetch_summary` is added as an additive
`bars.v1` readback for date-range success payloads and structured failure
details. It reports bounded fetch windows, `request_more_data` count,
requested count cap, observed / filtered / returned counts, and whether the
range was truncated by `count_cap`, `source_exhausted`, or `timeout`.

Second implementation progress: date-range mode now treats `--count` as a
larger returned-bar safety cap, defaulting to 500 and allowing up to 5000 for
supported date-range reads. Count-only mode keeps the maximum of 500.

Third implementation progress: date-range mode now allows a narrow intraday
set, `5`, `15`, `30`, and `60`, using the same `bars.v1` source,
`range_alignment`, and `range_fetch_summary` fields as daily / weekly /
monthly ranges. Other intraday date ranges remain validation-guarded.

## Lane 2: Intraday date-range feasibility and contract

Status: complete for the narrow `5` / `15` / `30` / `60` implementation slice.

Count-only `tv bars` already accepts intraday timeframes such as `1`, `3`,
`5`, `15`, `30`, `45`, `60`, `120`, `180`, and `240`. Date-range mode is now
being widened narrowly to `5`, `15`, `30`, and `60` alongside `1D`, `1W`, and
`1M`.

Intraday date-range support should be planned as the same historical range
feature family as large-range batching. It has extra uncertainty because
TradingView retention, symbol entitlements, exchange behavior, and older
intraday availability can vary more than daily/weekly/monthly history.

The current slice unlocks only `5`, `15`, `30`, and `60` as stable intraday
date-range timeframes. Smaller or less-used intraday ranges such as `1`, `3`,
`45`, `120`, `180`, and `240` remain guarded. If retention,
entitlement, timeout, or source-exhaustion evidence is mixed for those
timeframes, they should stay guarded and source diagnostics should be improved
before exposing broader stable CLI behavior.

## Lane 3: Unified range coverage semantics

Status: planned.

Daily, weekly, monthly, supported intraday, and future intraday range reads
should share the same first-pass readback vocabulary:

- `requested_range`: the user's inclusive calendar date request;
- `returned_range`: the range actually returned in `bars[]`;
- `observed_range`: the unfiltered source range observed before final range
  filtering;
- `range_coverage_status`: the primary date-range coverage readback;
- `source_availability`: source success or unavailable reason;
- `wait_summary`: bounded wait and message counts;
- `range_alignment`: timeframe-specific timestamp semantics.

For future range-scale work, additive readback may include
`range_fetch_summary`, `fetch_window_count`, `request_more_count`,
`requested_count_cap`, `observed_count`, `filtered_count`, `returned_count`,
`range_truncated`, and `range_truncation_reason`. These are source
diagnostics, not trading judgments.

## Lane 4: Sample preparation workflow

Status: planned.

Docs and runtime skills should continue teaching `tv bars --from --to` as the
formal source-preparation entry point for historical bars:

- older source-guided examples and base-pattern studies use daily, weekly, and
  monthly bars when those are enough;
- short intraday reviews can use `5`, `15`, `30`, or `60` date-range support when the
  source contract reports it as available;
- downstream tools save raw `bars.v1` evidence and convert it into their own
  prepared schema explicitly;
- `tv` does not become a backtest artifact converter or strategy engine.

## Lane 5: Deferred and later candidates

The following remain deferred unless a separate plan changes the boundary:

- automatic historical export from selected-chart `tv range` plus `tv ohlcv`;
- Replay-based historical extraction;
- watch or JSONL compare;
- chart-backed compare;
- quote-data auto fallback;
- automatic source mixing;
- standalone `tv events`;
- binary split;
- MCP server work;
- daemon, dashboard, or trading-bot behavior;
- ranking, scoring, or buy/sell recommendations.

These are not rejected forever. They are separate themes because each would
change the operating model more than range-scale `tv bars` maturity.

## Current Plan

- `docs/plans/tradingview-cli-bars-intraday-range-feasibility.md`

The completed range-scale slices added machine-readable fetch and truncation
diagnostics, then raised the date-range `--count` cap to 5000. The current
slice narrows intraday date-range support to `5`, `15`, `30`, and `60` while
keeping other intraday timeframes guarded.
