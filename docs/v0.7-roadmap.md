# v0.7.0 roadmap draft

This document records the `v0.7.0` direction after the `v0.6.0` release.

Status as of 2026-05-06: `v0.6.0` has been released. `tv` has a command source
taxonomy, additive source metadata across the major read payloads, bounded
Desktop-backed `tv stream ...` controls, `tv readiness`, screenshot visual
evidence metadata, and root `tv --version` support. The first `v0.7.0`
implementation slice added `tv observe chart` as a readiness-plus-last-bar
JSONL observation workflow, its JSONL contract now has an opt-in live smoke,
and the lab-gated `tv bars` path has opt-in evidence tooling. Observation
workflow docs and scanner-backed fundamentals field enrichment are also
complete. `v0.7.0` has been released; the next active planning track is the
`v0.8.0` roadmap in `docs/v0.8-roadmap.md`.

## Goal

`v0.7.0` should make `tv` easier to use as an observation producer for agents.
An observation producer is a command that emits structured JSON or JSONL over a
bounded window so another process can decide what to do next. The CLI should
keep reading and reporting TradingView state; it should not become a daemon, an
MCP server, a dashboard, or a trading bot.

The preferred direction is:

1. keep one `tv` binary and continue using command source taxonomy instead of
   splitting Desktop-free and Desktop-backed commands into separate binaries;
2. add a workflow-level observation surface that combines readiness and bounded
   chart samples into one JSONL stream;
3. keep `tv stream ...` compatible and treat any new `observe` command as a
   higher-level wrapper rather than a replacement;
4. keep browserless bars and future event/calendar work evidence-gated.

## Lane 1: Pull-Based Observation Workflows

The first implementation is `tv observe chart`. It reads the current Desktop
chart target, emits an initial readiness event, then emits selected-chart
last-bar sample and heartbeat events over a bounded window. This lets agents
run one command, inspect whether the chart was ready, and consume a short chart
observation without inventing sleeps or manual command loops.

Good `v0.7.0` candidates:

- use the opt-in live smoke for the `tv observe chart` JSONL event sequence;
- reuse the bounded observation controls already familiar from `tv stream ...`;
- emit source taxonomy metadata and screenshot hints in each relevant event;
- keep `tv stream ...` stable for callers that want the lower-level stream
  commands directly.

Not good default candidates:

- unbounded observation by default;
- automatic screenshot capture as part of observation;
- mutation, symbol switching, tab activation, or account/page state changes.

## Lane 2: Desktop-Backed Diagnostics

`tv readiness` is now the first structured check for Desktop-backed workflows.
Do not jump immediately to a broad `tv diagnose`. Instead, use downstream
experience with `readiness`, screenshot failure details, and observe workflows
to decide whether a broader troubleshooting command would actually reduce
operator confusion.

Good `v0.7.0` candidates:

- document recurring readiness failure patterns if they appear in downstream
  use;
- add small readiness details only when they are needed by an observation
  workflow;
- keep `tv diagnose` deferred unless repeated evidence shows one command is
  needed to combine readiness, target discovery, screenshot hints, and common
  recovery guidance.

## Lane 3: Browserless Bars And Market Data

`tv bars` remains experimental and gated by `TV_EXPERIMENTAL_BARS=1`. It is
useful as a lab path for Desktop-free historical bars, but it should not be
stabilized just because it exists.

Good `v0.7.0` candidates:

- add evidence and opt-in smoke around `tv bars` stability;
- clarify `data_quality`, `freshness`, timeout, and malformed protocol
  failures;
- decide later whether browserless bars belong in a reusable market crate.

Deferred by default:

- stable browserless historical bars;
- browserless streaming;
- authenticated HTTP, cookie/session import, or login automation.

## Lane 4: Fundamentals, Events, And Calendar Reads

`tv fundamentals` and field groups provide basic Desktop-free fundamentals and
earnings-related fields. Further event work should be based on scanner metainfo
evidence, not on broad Desktop parity.

Current evidence:

- scanner metainfo confirms the current `earnings` and `dividends` field
  groups;
- additional earnings and dividend candidates have been added to the existing
  groups where they are scanner field bundles rather than a complete
  TradingView event calendar;
- future implementation should continue preferring small evidence-backed group
  additions before adding a standalone `tv events` surface.

Good candidates after this evidence pass:

- consider another narrow field group or read surface only when the source fields are
  stable enough and useful to downstream workflows;
- keep raw financial statement APIs, news feeds, and account-local calendar
  state out of scope until separately justified.

## Lane 5: Workflow Skills And Documentation

Runtime skills should teach agents how to use structured `tv` reads and JSONL
observation. They should not compensate for weak CLI behavior by requiring
manual sleeps, Computer Use-only steps, or private local environment details.

Good candidates:

- maintain `docs/observation-workflows.md` as the short guide for choosing
  between Desktop-free screening, Desktop-backed chart observation,
  screenshots, experimental bars, and fundamentals reads;
- keep `chart-analysis` and `market-data-interpretation` aligned with
  `tv observe chart` and the workflow guide;
- add small workflow examples that start with `tv readiness` or
  `tv observe chart`, then escalate to screenshots only when structured fields
  are insufficient.

Deferred by default:

- Codex app-only Computer Use workflow skills;
- broad workflow packs;
- MCP server or daemon packaging.

## Deferred by default

- `tv diagnose`;
- `tvb`, `tvd`, or other alternate binaries;
- MCP server work;
- daemon or background monitor behavior;
- trading bots, dashboards, or workflow packs;
- cookie/session import or export;
- raw TradingView endpoint primitives;
- broad generic UI automation expansion;
- public-stable crates.io publication promises.
