# v0.30.0 roadmap

This document records the direction after the `v0.29.0` release.

Status as of 2026-07-19: `v0.29.0` is released from commit `a774142`. Current
planning has moved to `v0.30.0`. The ordered inventory is
`docs/v0.30-work-items.md`. The active ExecPlan is renderer foreground
feasibility; no latency correction, public timing contract, foreground
transition, or retained-backlog implementation is authorized yet.

## Theme

`v0.30.0` focuses on chart-read observability and Desktop renderer readiness.

The first goal is to explain the slow tail observed in bounded v0.29 evidence
without assuming that chart readiness, transport, or process startup is the
cause. The second is to establish whether a bounded foreground transition
changes renderer readiness and which limited target-side restore observations
can be proved for dialog-oriented operations. The release should also contain
one independently useful product slice from the retained backlog unless the
owner explicitly accepts a diagnostics-only release.

Measurement still precedes timeout, wait, retry, and process-lifetime changes.
Desktop-free and Desktop-backed sources remain explicit. The CLI does not
automatically mix sources, rank evidence, recommend trades, or make trading
decisions.

## Chart-read latency attribution

Priority: highest. Status: test-only implementation, full non-live validation,
and focused implementation review complete. One owner-authorized bounded live
matrix completed 40/40 trials without failure or deadline stop. Focused
evidence review is green and the plan is archived with an explicit-trigger
defer; no correction is promoted.

Measure `ohlcv --summary --count 20` and `values` separately through their real
in-process operation paths. Directly observe fresh connection, the operation's
single Runtime evaluation, the enclosing operation, harness-payload
serialization, and whole in-process trial time. Treat normalization and other
unattributed time only as labeled saturating residuals; do not claim separate
CDP send, response-wait, remote-expression, or process-startup timing where the
current ownership boundaries cannot prove it.

Source inspection already establishes that both operations issue one
synchronous Runtime evaluation and contain no explicit operation-side polling
loop. Therefore the plan must not label the v0.29 slow tail as polling or chart
readiness before new evidence proves it. Measurement must retain one absolute
outer budget, fixed cohorts, public-safe aggregate evidence, and no retry.

The first slice adds no public timing field. It may introduce internal typed
observations and ignored deterministic/live probes only when ordinary commands
remain unchanged and observers are absent by default.

## Evidence-gated latency correction

Priority: conditional after attribution. Status: deferred. Reopen only after a
chart read above one second, a chart-read timeout, or a `method_call` failure
stage is observed in ordinary operation or a later bounded run.

After focused evidence review, promote at most one correction with its own
ExecPlan. Possible outcomes include an operation-specific readiness or timeout
correction, a failure-only phase diagnostic, a stable internal phase vocabulary,
a separately reviewed public timing contract, routing to Desktop renderer work,
or a documented no-go/defer.

Public `--timing` is not the default next step. It is considered only if the
measured phase is stable, public-safe, and actionable for a user or agent.
Changing timeout values merely because the outer harness reached 12 seconds is
not acceptable.

## Renderer lifecycle and foreground feasibility

Priority: high after latency attribution. Status: test-only implementation and
full non-live validation complete; focused implementation and correction review
green. Exact two-target owner approval is pending and no live transition has
run.

Investigate Desktop app-tab ownership, CDP target identity, document
visibility, timer throttling, and a bounded `Page.bringToFront` or equivalent
transition. The study is shared infrastructure research for dialog-oriented UI
operations, not an indicator-search implementation plan.

Any live transition requires distinct disposable probe and restore targets and
separate owner approval. The plan may verify only the matching restore API
call, marker cleanup, and allowlisted target-side observations; it must not
claim that the visible Desktop app tab, OS focus, or window order was restored
without a separate machine-readable readback. It must stop on ambiguity or an
unknown transition outcome. A successful feasibility result does not itself
authorize indicator search, a shared session, or a broker.

## Agent workflow guidance

Priority: follow the owning evidence or implementation slice. Status: no
standalone major slice.

Retain the v0.29 target-handoff rule: resolve the intended target once, reuse
its `target_cli_args`, and resolve again after selection failure, target-set
change, or an intentional chart change. Clarify that ambiguous selection is a
deliberate fail-closed result and is not repaired by retry.

Do not publish generic larger timeout advice before attribution. Update runtime
skills in the same slice as any actionable latency or renderer contract rather
than creating a detached documentation program.

## User-facing product slice

Priority: required before completion audit unless explicitly declined by the
owner. Status: selection research follows the two technical investigations.

Compare retained candidates by user value, source stability, destructive
risk, dependency scope, and ability to close within v0.30. Candidates include
event date ranges and source availability, Replay screenshot attachment,
remaining intraday bars ranges, Screener column reset, safe new Pine script
naming and save, a complete calendar source, and explicit Replay or historical
export expansion.

Select at most one candidate through a short source-and-workflow review, then
create a self-contained implementation ExecPlan. Do not use this requirement
to force a weak candidate: if none meets the gate, record the no-go and require
an explicit owner decision before a diagnostics-only release.

## Maintained defers

Pre-dispatch retry remains deferred. Two bounded v0.29 runs observed no
`target_list`, `websocket_connect`, or `method_call` transient failure. Reopen
only after ordinary operation or a later bounded probe records the existing
trigger.

Shared session and broker work remain gated. The observed 36 ms whole-process
p50 removes connection latency as sufficient justification. Renderer lifecycle
or stale-event evidence may inform a later policy decision, but neither silently
promotes a background process.

Public recovery metadata, generalized waits, method-post-dispatch restart,
MCP, daemon operation, binary splitting, cookie/session import, login
automation, trading bots, automatic source mixing, ranking, scoring,
recommendation, and buy/sell output remain excluded or separately gated.

## Ordered execution

1. Complete and review chart-read latency attribution.
2. Promote at most one evidence-backed latency correction or record defer.
3. Complete and review renderer lifecycle and foreground feasibility.
4. Select and implement at most one independently useful retained-backlog item.
5. Run the v0.30 completion and architecture audit.
6. Prepare release artifacts only after the audit is green.

The two investigations are technically independent, but run them serially by
default so Desktop live evidence, approvals, and worktree state remain easy to
attribute.

## Quality gates

Every implementation slice requires focused deterministic tests, the full Rust
baseline, public hygiene, contributor-guide parity, and synchronized stable
docs and runtime skills when behavior changes. Live probes are ignored,
explicitly gated, bounded, owner-approved, and aggregate-only.
