# v0.22.0 roadmap draft

This document records the `v0.22.0` direction after the `v0.21.0` release.

Status as of 2026-05-27: `v0.21.0` is treated as released. `tv bars
--from/--to` is now a mature Desktop-free historical range source for daily,
weekly, monthly, and the narrow intraday set `5`, `15`, `30`, and `60`.
`v0.22.0` implementation lanes are complete enough for a pre-release
completion and architecture audit.

## Theme

`v0.22.0` is about observation and export workflow maturity.

The goal is not to rush another small release for documentation polish only.
The goal is to make the existing evidence surfaces easier to connect in real
workflows without hiding where data came from. `tv bars`, scanner reads,
snapshot / compare, selected-chart quote, observe / stream JSONL events,
screenshots, selected-chart historical export, and Replay extraction each have
different source boundaries. `v0.22.0` should make those handoffs explicit
instead of adding automatic fallback or source mixing.

## Lane 1: Evidence follow-up workflow

Status: complete for `v0.22.0`.

`tv snapshot` and `tv compare` can already point users toward follow-up
evidence, but the surrounding workflow should be clearer for humans and
agents. Follow-up hints are advisory readback: they describe possible next
checks, but they do not execute commands, switch charts, combine sources, or
make recommendations.

This lane should clarify when to use:

- `tv bars --from/--to` for reproducible Desktop-free historical bars;
- scanner-backed snapshot / compare for Desktop-free quote evidence;
- `tv quote --source chart` for a selected-chart quote check;
- `tv observe chart` or `tv stream ...` for bounded selected-chart JSONL
  observation;
- `tv screenshot` when visible chart state is the evidence needed.

The workflow should remain command-explicit. If an agent runs a follow-up, it
should report the command, source metadata, and relevant contract marker
rather than presenting blended evidence as one source.

The implementation adds advisory source metadata to existing `snapshot.v1` and
`compare.v1` `follow_up_hints[]`. Hints remain possible next evidence checks,
not automatic execution, source mixing, ranking, or recommendations.

## Lane 2: Watch / JSONL compare

Status: complete for the first `v0.22.0` slice.

The first `v0.22.0` implementation slice adds bounded
`tv watch compare <SYMBOL>...`. This is not a daemon, trading bot, or generic
realtime feed. It is a short-window observation workflow for a known candidate
set, with explicit stop conditions and machine-readable events.

The contract should define:

- event kinds and command-local contract marker;
- input candidate list and source selection rules;
- duration, max event, and interrupt behavior;
- sample, heartbeat, and final summary events;
- per-symbol source metadata and public-safe counters;
- log-writing expectations, if logs are supported;
- what happens when one symbol is unavailable, partial, or stale.

The first implementation uses Desktop-free scanner-backed quote evidence only.
It builds on the existing `observe_chart.v1` and `stream.v1` event lessons,
especially readiness, sample, heartbeat, summary, bounded controls, and
public-safe metadata, while keeping selected-chart sources out of the watch
log.

## Lane 3: Selected-chart historical export

Status: complete for the feasibility readback slice.

Selected-chart historical export is different from `tv bars`. It depends on
TradingView Desktop state, selected chart, visible range, symbol, timeframe,
and CDP-backed reads. It can be useful, but it must not become a hidden
fallback for browserless historical bars.

This lane should first produce a feasibility / contract plan for explicit
selected-chart export:

- how `tv range` moves the visible range;
- what `tv ohlcv` is contractually allowed to return;
- whether an export command can prove it read the requested selected-chart
  range;
- how target selection, Desktop readiness, and multiple windows are reported;
- how partial export, stale chart state, and unsupported views are surfaced.

The expected direction is an explicit Desktop-backed export workflow, not an
automatic substitute for `tv bars --from/--to`. The current slice should decide
what evidence is needed before such a workflow can become stable; it should not
add a stable export command yet.

The first implementation adds selected-chart export evidence readback to
existing commands rather than creating an export command. `tv ohlcv` reports
selected-chart context, returned bars range, and a conservative range-match
diagnostic. `tv range` reports itself as a visible-range operation. These
fields make feasibility inspectable while keeping `tv bars --from/--to` as the
Desktop-free historical bars source.

## Lane 4: Replay-based extraction

Status: complete for the feasibility / evidence readback slice.

Replay-based extraction is even more stateful than selected-chart export. It
depends on Replay mode, UI state, symbol, timeframe, start point, step
controls, and interruption behavior. It should therefore start as a safety and
feasibility plan, not as a stable export command.

This lane should answer:

- whether Replay mode can be detected reliably;
- which operations are read-only and which mutate chart state;
- how start, step, stop, and restore behavior are represented;
- whether extraction output can be bounded, summarized, and made public-safe;
- how failures avoid exposing raw target ids, local state, or account-local
  metadata.

Replay extraction should not be documented as a replacement for `tv bars`.

The implementation adds additive readback to existing `tv replay ...` commands
instead of creating an export command. `tv replay status` is readable as a
Desktop-backed Replay state read, while `start`, `step`, `stop`, `autoplay`,
and `trade` are readable as Desktop-backed Replay state operations. The output
exposes `replay_context`, selected-chart context where available, and operation
metadata so a future extraction workflow can be evaluated without source
mixing.

## Lane 5: Deferred and later candidates

The following remain deferred unless a separate plan changes the boundary:

- quote-data auto fallback;
- automatic source mixing;
- chart-backed compare as a broad stable command;
- standalone `tv events`;
- remaining intraday date-range support for `1`, `3`, `45`, `120`, `180`,
  and `240`;
- automatic historical export as a stable release feature before its
  feasibility contract is proven;
- Replay extraction as a stable release feature before its feasibility
  contract is proven;
- binary split;
- MCP server work;
- daemon, dashboard, or trading-bot behavior;
- ranking, scoring, or buy/sell recommendations.

These are not rejected forever. They are separate themes because each changes
the operating model more than observation / export workflow maturity.

## Current Plan

- `docs/plans/tradingview-cli-v0.22-pre-release-audit.md`

The current slice audits the completed `v0.22.0` workflow lanes before release
readiness. It checks contracts, docs, tests, source boundaries, private-data
hygiene, and architecture posture, including whether any module has grown
enough to require a dedicated refactor before release.
