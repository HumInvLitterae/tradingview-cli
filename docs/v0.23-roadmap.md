# v0.23.0 roadmap draft

This document records the `v0.23.0` direction after the `v0.22.0` release.

Status as of 2026-05-28: `v0.22.0` is treated as released. `v0.23.0`
implementation is open, selected-chart historical export has been added, and
the current slice implements a bounded Replay step log.

## Theme

`v0.23.0` is about explicit export and chart workflow maturity.

`v0.22.0` made several Desktop-backed and Desktop-free evidence surfaces
easier to read: bounded `tv watch compare`, selected-chart `tv ohlcv` /
`tv range` readback, Replay readback, and advisory follow-up hints. The next
step is to turn that evidence into explicit workflows where useful, without
hiding source changes from the user.

The key boundary remains: `tv bars --from/--to` is the Desktop-free historical
bars source. Selected-chart export, Replay extraction, and chart-backed compare
are Desktop state dependent workflows. They may be useful, but they must not
become hidden fallbacks for `tv bars`, scanner-backed reads, or quote-data.

## Lane 1: Selected-chart historical export command

Status: complete for the first `v0.23.0` slice.

`tv range` can move the visible range of the selected TradingView Desktop
chart, and `tv ohlcv` can read bars from that selected chart. `v0.22.0` added
readback that reports visible range, returned bars range, and conservative
range-match diagnostics. `v0.23.0` should use that foundation to evaluate and
then implement an explicit Desktop-backed export workflow.

The first implementation is a narrow `tv export chart-bars` command. It prints
the export result to stdout as the normal JSON envelope and does not write
files. The workflow separates three facts in the output:

- what visible range the user requested;
- what selected-chart state and visible range were observed;
- what bars were returned, and whether they overlap the observed visible
  range.

This lane should not claim that selected-chart export is the same as
Desktop-free `tv bars --from/--to`. It should report Desktop state dependency,
target selection, symbol, timeframe, returned range, and any ambiguity in a
public-safe shape.

## Lane 2: Replay extraction workflow

Status: current `v0.23.0` slice; implementation in progress.

`tv replay status/start/step/stop` now exposes Replay state and operation
metadata. Replay extraction remains more stateful than selected-chart export
because it changes the chart's Replay state and depends on UI controls,
symbol, timeframe, start point, and interruption behavior.

This lane should define a step-log contract before any stable extraction
command is exposed. A step log is a bounded record of Replay state before and
after each step, not a trading judgment. The workflow should define start
state, stop behavior, partial runs, failure details, and whether `tv ohlcv` or
screenshot evidence can be attached without automatic source mixing.

The current slice adds `tv replay log --steps <N>` as a bounded JSONL workflow.
It keeps `tv replay export` out of scope, does not start or stop Replay
automatically, and records readiness, per-step state, final end reason, and
public-safe failure details with `contract_version: "replay_step_log.v1"`.

## Lane 3: Chart-backed compare

Status: planned as a later `v0.23.0` candidate.

The current `tv compare` is scanner-backed and Desktop-free. A chart-backed
compare workflow would use selected-chart evidence, such as chart quote or
selected-chart bars, and should therefore be a separate source contract.

This lane should decide whether chart-backed compare is useful as a stable
command, a documented recipe, or a follow-up workflow driven by existing
commands. It must keep Desktop-free scanner compare, chart quote, `tv ohlcv`,
and `tv bars` visibly separate.

## Lane 4: Standalone `tv events` feasibility

Status: planned as feasibility work only.

Event-style data such as earnings, dividends, or calendar events may deserve a
standalone surface. This lane should investigate whether such data can be read
as a public-safe source with stable source metadata and useful failure
details.

The first step is feasibility and contract planning. `tv events` should not
be treated as a ranking engine, recommendation system, quote fallback, or bars
fallback.

## Lane 5: Deferred and later candidates

The following remain deferred unless a separate plan changes the boundary:

- quote-data auto fallback;
- automatic source mixing;
- automatic chart export that silently substitutes for `tv bars`;
- broad chart-backed compare without a source-separated contract;
- Replay extraction as a stable command before the step-log contract is
  proven;
- remaining intraday date-range support for `1`, `3`, `45`, `120`, `180`,
  and `240`;
- binary split;
- MCP server work;
- daemon, dashboard, or trading-bot behavior;
- ranking, scoring, or buy/sell recommendations.

These are not rejected forever. They are separate themes because each changes
the operating model more than explicit export and chart workflow maturity.

## Current Plan

- `docs/plans/tradingview-cli-replay-step-log-contract.md`

The current slice implements `tv replay log --steps <N>` as a bounded JSONL
Replay workflow. It preserves the boundary between Replay state-changing
selected-chart operations and Desktop-free historical bars from
`tv bars --from/--to`.
