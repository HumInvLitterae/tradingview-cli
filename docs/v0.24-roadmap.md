# v0.24.0 roadmap draft

This document records the `v0.24.0` direction after the `v0.23.0` release.

Status as of 2026-06-03: `v0.23.0` is treated as released. Launch process
handling, `tv bars` symbol usability, narrow `tv events` symbol-scoped
readback, pre-release architecture audit, and runtime skill context cleanup
have completed their `v0.24.0` slices. The current work is `v0.24.0` release
readiness.

## Theme

`v0.24.0` is about operational robustness and user input clarity.

`v0.23.0` added explicit selected-chart export and bounded Replay step logs.
The next release should make the tool easier to operate reliably through
agents and downstream wrappers. The first issues are practical: `tv launch`
can behave differently from a manual launch in some environments, and users
can easily forget that `tv bars` historically needs exchange-qualified
symbols.

The release should fix those operator-facing problems first, then revisit the
highest-value deferred workflow candidates. Those candidates are still useful;
they are simply less urgent than making existing launch and historical bars
workflows hard to misuse.

## Lane 1: Launch process handling

Status: complete for the first `v0.24.0` implementation slice.

`tv launch` should start or reuse TradingView Desktop without unexpectedly
terminating the app. The report from downstream is not that agents fail to
notice a crash; the concern is that the CLI/agent launch path itself may treat
the process in a way that causes TradingView Desktop to exit, while a manual
launch works.

This lane should investigate and harden:

- direct binary spawn versus macOS app launch through `open`;
- process handle and child-process lifetime behavior;
- existing-CDP reuse versus starting a new process;
- `--kill-existing` remaining opt-in only;
- payload and warning wording when launch succeeds as a command but CDP does
  not become ready.

The first implementation should not add daemon behavior, automatic restart, or
implicit process killing. It should make the launch method safer and the
result easier for agents to interpret.

Implemented direction: on macOS, the normal no-path launch uses the system app
launcher instead of direct binary spawn. Explicit `--path` remains direct
spawn, and `--kill-existing` remains opt-in.

## Lane 2: `tv bars` symbol usability

Status: complete for the first `v0.24.0` implementation slice.

`tv bars` is the Desktop-free historical bars source, but it currently teaches
`tv bars <EXCHANGE:SYMBOL>`. Users and agents often type bare symbols such as
`AAPL`. The ideal behavior is to accept bare symbols when they can be resolved
safely and to fail clearly when they cannot.

This lane implements:

- bare-symbol resolution through Desktop-free symbol search;
- success readback that separates the requested symbol from the resolved
  `EXCHANGE:SYMBOL`;
- ambiguous/not-found failure details with candidate full names;
- help and docs that make the `EXCHANGE:SYMBOL` requirement clear when
  resolution cannot safely choose one.

The implementation uses the first exact-symbol candidate from TradingView
search, then reports `requested_symbol`, `resolved_symbol`, `symbol`, and
`symbol_resolution`. It must not use the selected chart or fall back to scanner
quote, quote-data, Replay, or chart export.

## Lane 3: High-priority workflow candidates

Status: narrow `tv events` is complete for `v0.24.0`; release readiness is in
progress.

The following are worth keeping inside the `v0.24.0` roadmap after the launch
and bars usability slices:

- standalone `tv events` for narrow symbol-scoped earnings / dividends event
  readback using scanner-backed fundamentals fields;
- chart-backed compare as a source-separated Desktop-backed workflow, not as
  a hidden fallback for `tv compare`;
- Replay export or Replay evidence attachment, only after the bounded step-log
  contract proves safe enough;
- remaining intraday `tv bars --from/--to` timeframes, if retention and count
  behavior can remain bounded and readable.

The `tv events` first slice is not a full event calendar. It shapes existing
scanner fundamentals fields into `events.v1`, keeps the source marker as
`scanner_fundamentals_rest`, and does not infer timezone, before/after-market,
confirmed/estimated, ranking, recommendation, or trading judgment.

## Lane 4: Deferred and later candidates

The following remain deferred unless a separate plan changes the boundary:

- quote-data auto fallback;
- automatic source mixing;
- daemon, dashboard, or trading-bot behavior;
- MCP server work;
- binary split;
- ranking, scoring, or buy/sell recommendations.

These are separate because they change the operating model more than launch
robustness, symbol input clarity, or explicit workflow evidence.
