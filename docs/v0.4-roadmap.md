# v0.4.0 roadmap and release readiness

This document records the direction and release-readiness state for `v0.4.0`
after the `v0.3.0` release.

Status as of 2026-04-30: the first post-`v0.3.0` market-read lane is complete
and `v0.4.0` release readiness is prepared. The release covers Desktop-free
scanner quote improvements, batch quote, scanner scan, scanner metainfo,
explicit quote source selection, typed Rust API documentation, Desktop-free
historical bars feasibility notes, and runtime market-data interpretation
skills.

Patch status as of 2026-05-01: `v0.4.1` release readiness is prepared for the
chart-source quote stale-bar guard. This patch keeps the `v0.4.0` market-data
scope unchanged and only publishes the `tv quote <SYMBOL> --source chart`
readiness hardening.

Post-release note: `v0.4.x` is now closed. The next roadmap source of truth is
`docs/v0.5-roadmap.md`.

## Goal

`v0.4.0` should make market data reads more useful without depending on a
TradingView Desktop chart target, while keeping the CLI's mutation and UI
automation boundaries conservative.

The preferred direction is:

1. expand Desktop-free market data reads where scanner or public metadata
   endpoints already provide stable evidence;
2. keep upstream PR monitoring lightweight and targeted instead of restarting a
   broad migration sweep;
3. keep Desktop-free historical bars / OHLCV in the research lane until the
   undocumented WebSocket path is proven safe enough for a lab command;
4. review the internal Rust crate APIs that became reusable during `v0.3.0`;
5. leave account mutations, UI automation, and chart-state operations in their
   existing guarded adapter boundaries unless a later plan proves a safer API or
   storage replacement.

## Work order

### 1. Market data reads

The first `v0.4.0` candidate should be market data read polish. This is the
highest downstream-value lane because it reduces dependence on TradingView
Desktop state for quick symbol checks.

Current state:

- `tv info <SYMBOL>` is Desktop-free and uses TradingView symbol search
  metadata.
- `tv quote <SYMBOL>` defaults to the Desktop-free scanner-backed path and now
  includes an additive `extended_hours` object for premarket and postmarket
  values when TradingView returns them. It also exposes scanner `time`,
  `update_mode`, and parsed `delay_seconds` metadata when available.
- `tv quote <SYMBOL> --source chart` explicitly uses the selected
  TradingView Desktop chart feed, and `--source auto` is chart-first with
  scanner fallback only when chart access is unavailable before mutation.
- `tv quotes <SYMBOL>...` is available as an ordered batch read. It preserves
  input order and embeds the same quote payload shape as `tv quote <SYMBOL>`
  for each successful item.
- `tv scanner scan --columns ...` can request confirmed scanner extended-hours
  fields directly, keeping them in each row's `field_values` object.
- `tv scanner metainfo` is available as a field-discovery read. It reads scanner
  metadata rather than prices, so it is not affected by quote freshness.
- `tv quote` without a symbol remains a current-chart read through CDP.
- `tv ohlcv` remains a current-chart bars read through CDP.

Near-term candidates:

- Treat scanner REST watchlist-style reads as sufficient for current known
  operator needs. Expand scanner discovery only when a concrete workflow needs
  another field and scanner metainfo or endpoint evidence shows the field is
  safe to expose.
- Keep symbol resolution behavior shared between `info`, `quote`, and scanner
  reads where possible.
- Continue making freshness and feed-mode metadata explicit where TradingView
  returns it. Do not invent a session field unless TradingView provides a clear
  source.

Acceptance for this lane should be additive JSON fields or CLI options that do
not break existing payloads. Regular-session top-level fields should keep their
current meaning; extended-hours values should stay nested or explicitly named.
Credential-free scanner price reads are useful for screening, but they are not
realtime entitlement guarantees. Exchange rules, TradingView feed selection,
and market-data subscription state can affect freshness. Execution-grade
realtime data or authenticated entitlement-aware reads need separate research.

### 2. Desktop-free historical bars feasibility

Desktop-free OHLCV would be valuable, but the first feasibility pass is now
complete and did not find a stable-enough endpoint to promote directly into the
Rust CLI.

Research questions:

- Is there a credential-safe endpoint for historical bars that works without
  exporting cookies or session storage?
- Does it return enough market metadata to avoid silent exchange or session
  mismatches?
- Can it preserve the current `tv ohlcv` meaning, or would it need a separate
  symbol-targeted command shape?

Boundaries:

- Do not add direct HTTP account mutation.
- Do not import/export cookies or automate login.
- Do not replace current-chart `tv ohlcv` unless the Desktop-free path is
  clearly equivalent or a new command shape is explicitly planned.

If evidence is weak, keep `tv ohlcv` as a chart-dependent command and document
the boundary instead of forcing a replacement.

Current disposition:

- `tv ohlcv` remains a selected-chart command backed by the TradingView
  Desktop page-session chart bars collection.
- Desktop-free historical bars / OHLCV feasibility is complete for now, but no
  stable Rust CLI command has been implemented. This is not canceled; it is
  deferred as a research candidate.
- Browserless TradingView WebSocket bars are a `research_candidate`, not
  `safe now`. The protocol is undocumented and needs separate live smoke,
  freshness/entitlement checks, and a lab-gated design before implementation.
- If implemented later, the likely public surface should be a separate
  symbol-targeted command such as `tv bars <SYMBOL> --timeframe <TIMEFRAME>
  --count <N>`, not a silent change to `tv ohlcv`.

Comparable-project note:

- `fiale-plus/tradingview-mcp-server` main currently focuses on scanner,
  symbol metadata, and technical-analysis style reads.
- Its open PR #47, `feat(lab): experimental WebSocket tools — bars,
  stream-quotes, stream-bars`, contains the experimental implementation for
  historical bars and bounded quote/bar streaming. The design is useful
  evidence because it separates WebSocket protocol framing, chart/quote
  sessions, parsing, and tool-facing commands, gates the feature behind an
  experimental environment variable, and bounds both bar counts and streaming
  duration.
- This repository should treat that PR as a research input, not as a stable
  feature template. The implementation has an anonymous-token path, but it also
  has optional session-cookie configuration knobs and relies on an undocumented
  TradingView WebSocket protocol.

### 3. Upstream PR monitoring

Open upstream PRs were rechecked on 2026-04-29 with:

    gh pr list -R tradesdontlie/tradingview-mcp --state open --limit 100 --json number,title,updatedAt,createdAt,url,author,isDraft

The current open PR count is 57. This is a live number and should be refreshed
before making future upstream-driven decisions.

Notable current deltas:

- #120, `security: gate ui_evaluate behind env flag`: Rust already gates
  `tv ui eval` behind `TV_ALLOW_UNSAFE_UI_EVAL=1`, so this is covered unless a
  later review finds a stricter safety requirement.
- #118 / #117, chart scroll-to-date and screenshot output-path fixes: worth
  checking only if chart navigation or screenshot output becomes a concrete
  `v0.4.0` priority.
- #114 / #110 and related Windows Store/MSIX launch PRs: Rust has current
  Windows smoke evidence and should treat this as compatibility monitoring, not
  a default new implementation lane.
- #112, indicator `alertcondition()` alert creation: Rust has a narrower guarded
  implementation with readback. Do not expose upstream-style raw primitives
  unless a later plan proves they are safe.
- workflow bots, dashboards, rule packs, Docker/MCP packaging, and broad trading
  helper PRs remain outside the core CLI by default.

For `v0.4.0`, upstream work should be targeted monitoring. Do not start a broad
old-bridge PR migration sweep unless new evidence shows a missed core CLI
surface or a regression.

### 4. Internal Rust API review

The `v0.3.0` refactor left the workspace in a useful internal shape:

- `tradingview_core`: typed errors, JSON envelopes, and exit codes.
- `tradingview_model`: I/O-free request models, validation, target resolution,
  payload shaping, and fallback policy.
- `tradingview_market`: Desktop-free symbol search, symbol metadata, and quote
  reads, now with typed read-result APIs plus JSON wrappers for CLI
  compatibility.
- `tradingview_scanner`: Desktop-free scanner hotlist, scan, and metainfo
  reads, now with typed read-result APIs plus JSON wrappers for CLI
  compatibility.
- `tradingview_pine`: Desktop-free Pine analysis/check support.
- `tradingview_cdp`: CDP client, target discovery, runtime evaluation, input,
  and screenshot primitives.

For `v0.4.0`, the question is not whether every crate is public-stable. They are
still internal. The useful work is to review which APIs are already stable
enough for downstream reuse and which are still CLI-payload-shaped internals.

Likely review targets:

- `tradingview_market` and `tradingview_scanner`, because Desktop-free market
  reads are the next main product lane. The first typed API boundary pass is
  complete, and `docs/rust-api.md` now documents the preferred typed Rust
  surface. A later pass can add stronger field-specific value types if
  downstream consumers need them.
- `tradingview_model`, to ensure it stays an I/O-free model/policy boundary
  rather than accumulating live execution behavior.
- `tradingview_cdp`, only if a downstream consumer needs lower-level Desktop
  target control.

Do not publish crates or promise stable Rust API compatibility without a
separate plan.

### 5. API/storage stabilization

API/storage-backed replacements remain useful, but `v0.4.0` should avoid
turning this into an open-ended DOM replacement project.

Good candidates:

- small read-only or storage-backed improvements with clear readback;
- scanner/market data columns that are already endpoint-proven;
- bug-driven replacements where DOM behavior is visibly failing.

Poor candidates:

- raw account mutation primitives;
- payloads requiring saved account identifiers in user-facing input;
- UI-only visual behavior where the visible page is the source of truth;
- broad generic filter editors without stable schema evidence.

The existing rule remains: mutation commands must not report success without a
post-check.

## Likely next slices

The v0.4.0-oriented slices, scanner extended-hours columns, scanner
metainfo field discovery, ordered batch quotes, explicit quote source
selection, typed market/scanner API documentation, and Desktop-free historical
bars feasibility are complete. Runtime market-data and scanner/Screener
interpretation skills are also complete and packaged as runtime skills.

The scanner REST watchlist-style lane is sufficient for the current known
needs. Add more scanner REST features only when a concrete operator workflow
needs them and the field or endpoint evidence is clear.

Post-release candidates are:

1. A lab-gated Desktop-free `tv bars` prototype only if the project decides the
   undocumented WebSocket risk is worth a bounded experiment.
2. Targeted upstream PR delta check for #120, #118, and #117 if their surfaces
   become relevant.
3. Targeted runtime skill additions such as market-regime, peer-comparison, or
   due-diligence workflows only after downstream use shows a concrete need.

## Deferred by default

- direct HTTP account mutation;
- cookie or session export/import;
- login automation;
- generic non-numeric Screener filter editing;
- raw indicator-alert primitives;
- trading bots, dashboards, and workflow packs;
- broad MCP server work.
