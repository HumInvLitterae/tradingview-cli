# v0.11.0 roadmap draft

This document records the `v0.11.0` direction after the `v0.10.0` release.

Status as of 2026-05-08: `v0.10.0` has been released. The `tv compare
<SYMBOL>...` payload now includes additive `summary` readback, and the stable
docs explain how `quotes`, `compare`, `snapshot`, `observe chart`,
chart-source quote, and screenshot fit together. The current phase is
compare contract metadata implementation for `v0.11.0`.

Downstream feedback after `v0.10.0` confirmed that the most useful next work is
not a new data source. It is making `compare` easier for downstream wrappers
and agents to consume safely while preserving raw per-symbol evidence.

## Theme

`v0.11.0` is about downstream-safe comparison contracts.

The goal is to strengthen `compare` as a machine-readable evidence packet
without turning it into ranking, scoring, recommendation, chart switching, or a
realtime multi-symbol feed.

## Lane 1: Compare Contract Readability

`tv compare <SYMBOL>...` remains the Desktop-free multi-symbol comparison
surface. Its raw `items[]` array is still the evidence source, while
`summary` is a scanability helper.

The leading implementation candidate is additive contract metadata:

- a command-local contract marker such as `data.contract_version:
  "compare.v1"`;
- a stable requested-order index on each item and each resolved-symbol summary;
- machine-readable per-symbol follow-up hints;
- summary-level field coverage for quote, info, fundamentals, and
  evidence-backed earnings/dividends categories.

These fields should help downstream tools join `compare` output back to their
input lists, guard fixtures against contract drift, and identify evidence gaps
without reinterpreting the whole payload.

## Lane 2: Follow-up Workflow Clarity

`compare` should continue to describe what evidence was collected and what
follow-up surfaces are available, not which security to buy or rank.

Follow-up should stay explicit and source-specific:

- `tv snapshot <SYMBOL>` for one-symbol Desktop-free detail;
- `tv observe chart --duration-ms ...` for selected-chart time-window
  observation;
- `tv quote <SYMBOL> --source chart` for single-symbol selected-chart quote
  follow-up;
- `tv screenshot` only when visual evidence is needed after structured reads.

Machine-readable hints should be enums or stable strings that name the
follow-up surface. They should not imply recommendation strength.

## Lane 3: Field Coverage And Missing Evidence

The `compare.summary` readback already reports section success counts and total
missing values. The next useful polish is to make missing evidence easier to
explain by category.

Initial coverage categories should be limited to current evidence:

- quote;
- info;
- fundamentals;
- earnings fields that already exist in fundamentals groups;
- dividend fields that already exist in fundamentals groups.

Do not infer financial meaning from missing values. Missing means unavailable
or null in the current scanner-backed read, not bad or good.

## Lane 4: Deferred Source Strategy

The following remain deferred unless a separate plan changes the boundary:

- ranking, scoring, or buy/sell recommendations;
- chart-backed compare;
- watch or JSONL compare;
- realtime multi-symbol feed;
- stable browserless bars;
- standalone `tv events`;
- `tv diagnose`;
- `tvb`, `tvd`, or other alternate binaries;
- MCP server work;
- daemon, dashboard, or trading-bot behavior;
- cookie/session import or export;
- raw TradingView endpoint primitives;
- public-stable crates.io publication promises.

Chart-source quote remains a correctness-first single-symbol follow-up source.
If the rare mismatch issue reappears, handle it in a patch lane separate from
`compare` contract polish.

## Current ExecPlan

- `docs/plans/tradingview-cli-compare-contract-metadata.md`

The current slice creates the first implementation plan for additive `compare`
contract metadata and then implements it without changing command-line options,
versions, dependencies, or release packaging.
