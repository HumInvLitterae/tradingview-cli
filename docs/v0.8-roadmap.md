# v0.8.0 roadmap draft

This document records the `v0.8.0` direction after the `v0.7.0` release.

Status as of 2026-05-07: `v0.8.0` has been released. `tv` now has
Desktop-backed observation through `tv observe chart`, opt-in live smoke tests
for chart observation and lab-gated bars, observation workflow documentation,
scanner-backed fundamentals enrichment, and the initial Desktop-free
`tv snapshot <SYMBOL>` evidence packet. The chart-source quote concurrency
audit ran after release and did not reproduce symbol mismatch in the opt-in
live smoke. `v0.9.0` planning can proceed with Desktop-free comparison as the
default direction.

## Theme

`v0.8.0` is about multi-source evidence packets for agent workflows.

An evidence packet is a single structured response that gathers related facts
from several read-only sources so a human or agent can inspect one symbol
without manually stitching together multiple commands. It should preserve
source, freshness, missing-value, and error metadata rather than hiding where a
piece of data came from.

## Lane 1: Symbol Snapshot

The first implementation candidate, `tv snapshot <SYMBOL>`, is implemented.

The initial snapshot is a Desktop-free, single-symbol JSON command. It gathers
the same practical evidence an agent commonly asks for before a first-pass
decision:

- scanner-backed quote data, including freshness metadata where available;
- symbol identity and metadata from the Desktop-free symbol info path;
- scanner-backed fundamentals using the existing default fields, groups, and
  explicit field validation.

The first implementation does not mutate the visible TradingView Desktop
chart, open tabs, take screenshots, start JSONL observation, or call the
lab-gated WebSocket bars path. Chart and visual follow-up are represented as
next-action hints, not embedded source changes.

## Lane 2: Observation Workflow Follow-Up

`tv observe chart` remains the Desktop-backed time-window observation command.
Do not broaden it immediately. Reevaluate its surface after `tv snapshot`
exists, because snapshot may reduce the need for agents to start chart
observation just to collect static quote, info, and fundamentals context.

Good follow-up candidates after snapshot:

- clearer guidance for when to use `snapshot` versus `observe chart`;
- optional additional observe modes only when downstream use shows a repeated
  need;
- small contract polish that keeps `observe chart` read-only and bounded.

Deferred by default:

- automatic symbol switching inside observe;
- automatic screenshot capture;
- daemon-like watch loops;
- replacing `tv stream ...`.

## Lane 3: Browserless Bars And Market Data

`tv bars` remains lab-gated and evidence-gated. It is useful as an experimental
Desktop-free historical bars path, but the project should not make it stable
or fold it into snapshot until its protocol behavior is better understood.

Good `v0.8.0` work is limited to evidence, documentation, and narrow fixes if
the lab smoke exposes a concrete contract issue. Stable browserless bars,
browserless streaming, authenticated HTTP, cookie/session import, and login
automation remain deferred.

## Lane 4: Fundamentals, Events, And Calendar Reads

Fundamentals and event-like scanner fields should support snapshot and the
existing `tv fundamentals` groups. The project should not add a standalone
`tv events` command until scanner evidence and downstream workflows justify a
separate surface.

Good candidates:

- expose existing fundamentals groups through `tv snapshot`;
- preserve raw scanner values for earnings and dividend fields;
- keep timezone, before/after-market, and publication-code interpretation out
  of the CLI unless TradingView returns a clear normalized field.

Deferred by default:

- a standalone `tv events` command;
- news feeds and full event calendars;
- raw financial statement APIs;
- authenticated or account-local reads.

## Lane 5: Documentation And Skills

Docs and runtime skills should clarify when to use a single read, a snapshot,
or a chart observation:

- use Desktop-free reads and `tv snapshot` for broad first-pass symbol context;
- use `tv observe chart` when selected-chart state over time matters;
- use `tv screenshot` only when structured fields are not enough;
- treat lab-gated `tv bars` as experimental evidence, not primary workflow
  evidence.

## Current ExecPlan

- `docs/plans/tradingview-cli-v0.9-roadmap-and-compare-planning.md`

The first `v0.8.0` implementation slice, `tv snapshot <SYMBOL>`, is complete.
The docs/skills follow-up and opt-in live contract smoke are also complete.
The pre-release audit found no release-blocking refactor need, and `v0.8.0`
has been released. The chart-source quote concurrency smoke passed at
near-concurrent widths 2 and 3 in one live Desktop session, with no
requested/observed/chart symbol mismatch and no restore or freshness failure.
That result does not make chart-source quote a realtime batch source; it fixes
the `v0.9.0` boundary so comparison planning should start Desktop-free and use
chart-source quote only as a single-symbol follow-up when selected-chart feed
evidence matters.

## Deferred by default

- chart-backed snapshot sources;
- automatic screenshot capture in snapshot;
- JSONL, watch, daemon, or background behavior for snapshot;
- stable browserless historical bars;
- browserless streaming;
- standalone `tv events`;
- `tv diagnose`;
- `tvb`, `tvd`, or other alternate binaries;
- MCP server work;
- trading bots or dashboards;
- cookie/session import or export;
- raw TradingView endpoint primitives;
- public-stable crates.io publication promises.
