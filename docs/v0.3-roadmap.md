# v0.3.0 roadmap

This document records the intended post-`v0.2.0` direction for the Rust-native
`tv` CLI. It is a roadmap, not a release promise. Each implementation slice
still needs its own evidence-backed plan before code changes.

## Goal

`v0.3.0` should make the CLI more reliable and reusable before expanding into
another broad feature wave.

The preferred direction is:

1. re-check open upstream pull requests from `tradesdontlie/tradingview-mcp`;
2. use the findings to pick high-value stability and compatibility slices;
3. continue replacing fragile DOM mutation paths with safer page-session API or
   storage-backed paths when evidence supports it;
4. investigate direct HTTP for credential-safe read-only surfaces that have a
   clear benefit without requiring a TradingView Desktop target;
5. design the binary/library crate split after the current command boundaries
   and API dependencies are better understood.

## Work order

### 1. Upstream pull request re-check

The first refreshed upstream PR inventory is now complete enough for `v0.3.0`
planning. The old JavaScript project still has open PRs, but the current high
priority Rust dispositions are documented: compatibility fixes are addressed or
deferred with evidence, Windows Store/MSIX launch has Windows v3 smoke evidence,
and workflow/helper PRs stay outside the core CLI by default.

The first refreshed note is
`docs/notes/upstream-pr-recheck-2026-04-27.md`.

Current outcome from that re-check:

- TradingView Desktop / Electron compatibility around CDP target detection is
  partially addressed: the CLI now defaults to `127.0.0.1`, skips initial CDP
  domain-enable calls, and exposes app-window targets for diagnostics.
- Target selection cleanup: `--target-id` is the explicit user-facing handoff;
  the old target-id environment fallback has been removed from the public
  contract.
- Windows launch behavior around Microsoft Store/MSIX installs has been
  verified for `TradingView.Desktop 3.1.0.7818` through the existing direct AppX
  path. The standalone Desktop installer remains the recommended launch path
  because Store/MSIX CDP startup can change with future TradingView Desktop,
  Electron, or Microsoft Store packaging updates. See
  `docs/notes/windows-store-msix-launch-boundary.md`.
- Indicator or Pine `alertcondition()` alert creation feasibility is recorded
  in `docs/plans/archives/tradingview-cli-indicator-alertcondition-feasibility.md`.
  Rust now has local discovery through `tv pine alertconditions [--file <PATH>]`
  and guarded create/preview through `tv alert create-indicator ... [--dry-run]`.
  Normal create remains narrower than upstream PR #112's raw primitive: it uses
  endpoint readback, omits saved-script ids from output, and fails before
  mutation when required input metadata cannot be resolved safely.
- Keep trading bots, dashboards, and workflow packs outside the core CLI unless
  a later plan proves a narrow command belongs in this repository.

Future upstream work should be monitoring, not another broad sweep, unless new
PRs appear or a Rust regression needs upstream evidence.

### 2. Non-public API and storage-backed stabilization

The `watchlist`, `alert`, and Screener storage work showed that some operations
are more reliable through TradingView's logged-in page-session APIs or saved
storage payloads than through visible DOM automation.

For `v0.3.0`, use that lesson selectively:

- Prefer API/storage-backed paths when they can be verified by readback and do
  not require exposing credentials, account-local identifiers, or raw payloads
  in docs.
- Keep DOM paths where the value is inherently visual, such as screenshot
  regions, visible chart/table reads, and UI-only diagnostics.
- Do not add generic DOM retries before checking whether the operation has a
  safer API or storage boundary.
- Preserve the current rule that mutation commands must not report success
  without a post-check.

The public-safe reference for these dependencies is
`docs/internal-tradingview-apis.md`.

### 3. Direct HTTP feasibility

Direct HTTP was the next research lane after the upstream re-check. The first
research pass started from the current direct HTTP usage and classified whether
any additional read-only candidate was worth implementing.

The first scope was credential-safe read-only surfaces where direct HTTP has a
clear operational benefit, such as market discovery reads that do not need the
local TradingView Desktop page state. The completed research plan is
`docs/plans/archives/tradingview-cli-direct-http-feasibility.md`, and the first
follow-up implementation added Desktop-free `tv info <SYMBOL>` reads plus
tighter `tv quote <SYMBOL>` resolution behavior.

Do not add direct HTTP account mutation, cookie import/export, session storage,
or login automation without a separate explicit plan and user approval.

### 4. Library crate split

The repository is still a CLI-first project, but the library split has moved
past the first mechanical CLI library-root boundary. The workspace now has
narrow internal crates for the core contract, Desktop-free read or analysis
surfaces, the shared I/O-free model layer, and the shared CDP connection
substrate: `tradingview_core`, `tradingview_model`, `tradingview_market`,
`tradingview_scanner`, `tradingview_pine`, and `tradingview_cdp`.

This is a good `v0.3.0` boundary. Further extraction should happen only when a
later plan proves a concrete dependency boundary, because the split should
reflect real module responsibilities rather than an abstract architecture
exercise.

The latest internal refactors split the `tv` binary from the library-owned
application runner, extracted CDP target discovery/runtime evaluation into
`tradingview_cdp`, and moved the `tradingview-cli` package under
`crates/cli/`. The repository root is now a virtual workspace. Domain operation
adapter modules remain under `crates/cli/src/ops/` until a later plan proves a
smaller domain boundary.

The first operation-adapter cleanup now splits the largest module, Screener,
behind `crates/cli/src/ops/screener.rs` and sub-surface modules under
`crates/cli/src/ops/screener/`. This is intentionally not a domain crate yet;
it is the intermediate shape that should make future pure storage/API or
normalization extraction easier to identify. The first deeper Screener split
moves validation implementation into `crates/cli/src/ops/screener/validation.rs`,
the next split moves storage-backed column operations into
`crates/cli/src/ops/screener/columns.rs`, and the remaining operation bodies
now live in `state`, `screens`, and `filters` modules. `engine.rs` remains as
the shared runtime/helper layer until a later slice proves a smaller
`runtime` or `storage` split is useful.

The same adapter-first rule now applies to Alert. `crates/cli/src/ops/alert.rs`
is a facade over `list`, `create`, `indicator`, `delete`, and `payload`
modules. This keeps page-session API details, DOM fallback policy, Pine
metadata resolution, and public-safe payload normalization separated without
pretending Alert is already a reusable domain crate.

Layout now follows the same pattern while keeping its historical facade name.
`crates/cli/src/ops/layout.rs` re-exports watchlist and pane operations, while
`watchlist.rs` owns watchlist API/DOM behavior and `pane.rs` owns pane
layout/focus/symbol behavior.

Pine now follows the same pattern for its CDP-dependent Editor operations.
`crates/cli/src/ops/pine.rs` continues to combine Desktop-free helpers from
`tradingview_pine` with Editor operations, while
`crates/cli/src/ops/pine/editor.rs` re-exports focused `runtime`, `source`,
`scripts`, and `compile` modules. This keeps Monaco/CDP helper code separate
from source editing, saved-script operations, and compile/report reads without
moving UI-dependent code into the Desktop-free `tradingview_pine` crate.

The same facade pattern now covers the medium adapters that had the same
mechanical cleanup shape. Drawing is split into validation, creation, read, and
lifecycle modules. Replay is split into validation, control, autoplay, trade,
status, and payload modules. Chart-dependent Market remains in the CLI package
but now separates Desktop-free delegation, chart quote/freshness logic, and
OHLCV reads. Generic UI automation is intentionally left out of this batch
because its unsafe-gated input surface has different safety constraints.

Generic UI automation is now handled as its own safety-focused adapter split.
`crates/cli/src/ops/ui.rs` stays as the compatibility facade, while DOM actions,
input events, selector lookup, and eval execution live under
`crates/cli/src/ops/ui/`. The unsafe eval authorization remains in the
application safety/dispatch layer instead of moving into the operation adapter.

The next refactor boundary is no longer another mechanical `ops` facade split.
The proven in-package `domain` layer has been extracted into
`tradingview_model` under `crates/model/`. This crate owns I/O-free request
interpretation, validation, target resolution, payload normalization/shaping,
and fallback policy for Watchlist, Alert, Replay, Drawing, and Screener. It is
named `model`, not `domain`, because the broader domain behavior lives across
service/client crates such as `tradingview_market`, `tradingview_scanner`, and
`tradingview_pine`; the model crate is the shared policy and data boundary
those layers can reuse without taking on CDP or HTTP dependencies.

`ops` remains in the CLI package as the executable TradingView adapter layer.
It owns CDP/runtime access, page-session API execution, DOM/UI fallback, live
state reads, and post-checks. `app/dispatch` may depend directly on
`tradingview_model::*` for pure validation and request construction, while
`ops::*` is reserved for executable TradingView operations.

The operation adapter boundary review is now documented in
`docs/operation-adapter-boundaries.md`. It treats most remaining `ops` code as
live execution adapters rather than missed model logic: chart state, Replay,
Drawing, Pine Editor, Screener UI/storage, watchlist/alert page-session
mutations, tab app-window actions, screenshots, and generic UI automation all
stay in the CLI package unless a future evidence-gated plan proves a safer
API/storage replacement. This is the preferred `v0.3.0` refactor boundary
before release readiness.

A bounded Screener filter storage mutation audit was completed after that
review. With a full-page Screener target, `filters modify --min/--max` now uses
saved-screen storage for simple `Condition` filters selected by index and
verifies by storage re-fetch. `filters add` and `filters modify --option`
remain UI-backed because no safe catalog or option value source has been proven
for raw storage payload construction. This is not a `v0.3.0` release blocker.
`tv screener open --full-page` now reuses an existing full-page Screener target
and returns `target_cli_args`. It also attempts CDP target creation, but current
TradingView Desktop evidence shows the standard new-target endpoint can reject
Screener page creation, so fully automatic full-page preparation remains a
non-blocking follow-up rather than a `v0.3.0` release blocker.

Likely direction:

- keep `crates/cli/src/main.rs` and CLI dispatch thin;
- keep application orchestration in `crates/cli/src/app/`, not in the binary
  entrypoint;
- keep typed errors, JSON envelopes, and exit-code mapping in
  `tradingview_core`;
- keep I/O-free request models, validation, target resolution, and payload
  shaping in `tradingview_model`;
- keep credential-free, Desktop-free market reads in `tradingview_market`;
- keep credential-free scanner reads in `tradingview_scanner`;
- keep Desktop-free Pine static/check helpers in `tradingview_pine`;
- keep CDP-dependent Pine Editor operations in the CLI package adapter modules;
- keep shared CDP target discovery, runtime evaluation, screenshots, and input
  event primitives in `tradingview_cdp`;
- keep command-specific modules grouped by capability;
- keep `ops` inside the CLI package as operation adapters;
- prefer API/storage replacement evidence or small shared helper extraction
  over creating another crate by default;
- avoid exposing unstable internal TradingView payload shapes as a public Rust
  API;
- define which types are library-stable and which remain crate-private.

## Non-goals for v0.3.0

- No MCP server.
- No full reimplementation of the original JavaScript bridge.
- No authenticated standalone TradingView API client.
- No cookie/session import or export.
- No account mutation through direct HTTP unless a later plan proves a safer
  boundary.
- No trading bot, strategy pack, or dashboard workflow inside the core CLI by
  default.

## Completion boundary

`v0.3.0` is ready to consider when:

- the upstream PR re-check remains monitored and the newest high-value PRs have
  clear Rust dispositions;
- the highest-priority compatibility fixes have either been implemented or
  explicitly deferred with evidence;
- direct HTTP has a documented feasibility outcome for the first read-only
  candidate set and its first symbol-read follow-up;
- the library crate split has stable internal boundaries for core contracts,
  Desktop-free market reads, scanner reads, Pine static/check helpers, and CDP
  target/runtime support;
- the binary/application boundary keeps `crates/cli/src/main.rs` thin and
  application dispatch in the CLI package library;
- README, CHANGELOG, release notes, and runtime skills reflect the final
  user-visible behavior.
