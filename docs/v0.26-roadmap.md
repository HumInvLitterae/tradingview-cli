# v0.26.0 roadmap

This document records the `v0.26.0` direction after the `v0.25.0` release.

Status as of 2026-07-10: `v0.25.0` is released. The workspace version remains
`0.25.0`, and dependency maintenance commits exist after the release tag. The
current work is the first `v0.26.0` implementation plan: hardening JSON and
JSONL output when a downstream pipe closes.

The ordered work inventory and later feature backlog are maintained in
`docs/v0.26-work-items.md`. That inventory is the durable reminder for work
that must not be lost when only one ExecPlan is active at a time.

## Theme

`v0.26.0` is about CLI robustness, I/O correctness, and measured
Desktop-free read efficiency.

The existing CLI surface is broad enough that correctness at process and
transport boundaries now matters more than adding another command
immediately. Reviews after `v0.25.0` found reproducible output failure on a
closed pipe, CDP events that can be discarded while a method response is
pending, timeouts that can be extended by unrelated traffic, HTTP and
WebSocket operations without explicit end-to-end deadlines, inconsistent
HTTP error classification, and sequential multi-symbol reads that do not
reuse an HTTP connection pool.

This is not a change of product direction. `tv` remains a single CLI with
explicit Desktop-free and Desktop-backed source boundaries. The release does
not add automatic fallback, automatic source mixing, ranking, or trading
decisions.

## Release gates

The work is deliberately ordered. A later gate should not begin while the
previous gate has unresolved tests, contract questions, or unreviewed changes.
Each gate receives its own ExecPlan when it becomes active; future ExecPlans
are not written in full now because earlier results may change their design.

### Gate 0: Current-source reset

Status: complete.

The contributor source list, continuity ledger, plan index, README roadmap
link, and completed `v0.25.0` release plan now point to the current state.
The reset changes documentation only and does not bump the package version.

### Gate 1: JSON and JSONL broken-pipe handling

Status: current plan.

Replace panic-prone `println!` and `eprintln!` output with explicit writes.
Closing a stdout consumer such as `head` must stop one-shot or streaming
output without a Rust panic, backtrace, duplicate error envelope, or continued
network polling. Broken stdout is normal consumer completion; a command that
was already failing retains its original failure status if stderr is closed.

Current ExecPlan:
`docs/plans/tradingview-cli-output-broken-pipe.md`.

### Gate 2: CDP event buffering and absolute deadlines

Status: planned after Gate 1.

Preserve Chrome DevTools Protocol events that arrive while a method response
is pending, and make response/event waits use one absolute deadline rather
than restarting the timeout after every unrelated message. This gate keeps
the existing sequential `&mut CdpClient` request model and does not add
concurrent CDP calls.

### Gate 3: Transport deadlines and HTTP client reuse

Status: planned after Gate 2.

Give public HTTP reads, CDP target discovery, CDP WebSocket connection, and
bars WebSocket connection explicit finite deadlines. Reuse a configured
`reqwest::Client` within each owning crate or top-level operation without
adding `reqwest` to `tradingview-core`. This gate does not add retries or
parallel requests.

### Gate 4: Bars heartbeat verification

Status: planned after Gate 3.

Use wire-format tests to determine whether the bars heartbeat response should
omit its trailing delimiter or include that byte in the declared payload
length. Change the protocol only after a failing invariant test establishes
the mismatch. A public-safe optional live smoke may supplement the fixture,
but raw frames or bars must not be stored in tracked files.

### Gate 5: HTTP error taxonomy

Status: planned after Gate 4.

Make validation, connection failure, timeout, remote non-success status, and
payload decoding map consistently to the existing `ErrorKind` and exit-code
contract. The core crate continues to own error kinds only; reqwest-specific
mapping remains in the crates that own HTTP calls.

### Gate 6: Measured bounded multi-symbol concurrency

Status: planned last.

After deadlines, connection reuse, and error classification are stable,
measure `quotes`, Desktop-free `compare`, and `events compare` with a local
deterministic server. If measurement supports the change, process symbols
with a small fixed concurrency limit while preserving input order, partial
success, first-error determinism, and source metadata. Do not parallelize
chart-backed compare because it mutates and restores selected-chart state.

## Release cut and feature continuation

Completing Gates 1 through 6 is sufficient to enter the `v0.26.0` pre-release
audit and release-readiness sequence. None of the retained feature candidates
is required to release `v0.26.0`.

After Gate 6, the project manager may explicitly promote one feature at a time
into a new ExecPlan. That decision must update this roadmap, the work-item
inventory, and the expected release scope before implementation starts. If no
feature is promoted, proceed directly to the pre-release audit.

The hardening sequence does not cancel product work. The preferred retained
feature order is:

1. event-range and source-availability expansion for `tv events` without
   pretending scanner fundamentals are a complete calendar;
2. opt-in Replay screenshot attachment with explicit artifact naming,
   location, cleanup, and per-step metadata;
3. richer Strategy Tester evidence while keeping visual screenshots separate
   from structured strategy, trade, and equity reads.

Other retained candidates are remaining intraday `tv bars --from/--to`
timeframes (`1`, `3`, `45`, `120`, `180`, and `240`), Screener column reset
and cleanup, and safe naming/saving for a new Pine script. Their scope and
acceptance requirements are recorded in `docs/v0.26-work-items.md`.

## Boundaries

The following remain deferred unless a later roadmap explicitly changes the
project model:

- quote-data automatic fallback;
- automatic mixing of scanner, bars, selected-chart, Replay, or screenshot
  evidence;
- automatic historical or Replay export beyond existing explicit commands;
- daemon, dashboard, or trading-bot behavior;
- MCP server work or binary splitting;
- ranking, scoring, or buy/sell recommendations.

## Validation posture

Every implementation gate should run focused tests first and then the normal
workspace baseline:

    cargo fmt --check
    cargo clippy --workspace --all-targets --all-features -- -D warnings
    cargo test --workspace
    cargo metadata --no-deps --format-version 1
    git diff --check

Network and Desktop smoke tests remain supplemental. A skipped smoke must
record the required environment and residual risk. No tracked document may
contain raw live payloads, raw bars, raw live or account-bearing WebSocket
frames, credentials, session identifiers, account-local identifiers, raw
target identifiers, or machine-specific absolute paths. Minimal synthetic
protocol fixtures without market data, identifiers, credentials, or
account-local content are allowed when deterministic wire-format tests need
them.
