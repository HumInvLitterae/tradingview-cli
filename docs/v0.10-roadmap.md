# v0.10.0 roadmap draft

This document records the `v0.10.0` direction after the `v0.9.0` release.

Status as of 2026-05-08: `v0.9.0` has been released. The first
Desktop-free comparison surface, `tv compare <SYMBOL>...`, is available with
opt-in live contract evidence. The next phase should use downstream feedback
before broadening `compare` or adding realtime surfaces.

Downstream feedback confirmed that the main v0.10 value is not another market
data surface. It is making `compare` easier for agents and downstream tools to
consume safely while preserving the raw item evidence.

## Theme

`v0.10.0` is about comparison workflow polish and evidence follow-up.

The goal is to make the `compare` / `snapshot` / chart-observation workflow
easier for humans and agents to use without prematurely turning comparison
into ranking, recommendation, chart switching, or realtime feed behavior.

## Lane 1: Compare Workflow Polish

`tv compare <SYMBOL>...` is the current Desktop-free multi-symbol evidence
packet. It preserves source metadata, per-symbol sections, section errors, and
missing-value summaries.

Good first follow-up candidates:

- additive machine-readable summary fields for `compare`, such as resolution
  summary, per-section ok/missing counts, and resolved symbol lists;
- workflow docs and runtime skills with a small decision table that makes
  `compare` versus `quotes` versus `snapshot` obvious;
- live smoke evidence from downstream environments before expanding the
  command surface.

Prefer readback over judgment. A summary should help downstream tools see
which symbols resolved, which sections succeeded, and what values are missing
without reinterpreting the raw `items` array.

Do not add scoring, ranking, or buy/sell recommendations by default. If
ranking becomes useful later, it should be explicit and educational rather
than presented as trading advice.

## Lane 2: Finalist Follow-up Workflow

`tv compare` should help narrow candidates. Follow-up evidence should remain
explicit and source-specific:

- `tv snapshot <SYMBOL>` for one-symbol Desktop-free detail;
- `tv observe chart --duration-ms ...` for selected-chart time-window
  observation;
- `tv quote <SYMBOL> --source chart` for single-symbol selected-chart quote
  follow-up;
- `tv screenshot` only when visual evidence is needed after structured reads.

Chart-source quote remains a single-symbol selected-chart read. It is not the
default multi-symbol comparison source.

## Lane 3: Realtime And Browserless Data Strategy

Multi-symbol realtime feeds, browserless streaming, and stable browserless
historical bars remain separate strategy work. They should not be folded into
`compare` without fresh evidence that the source is reliable enough and that
the workflow needs it.

`tv bars` stays lab-gated until its undocumented WebSocket path has stronger
evidence and clearer downstream value.

## Lane 4: Fundamentals And Events Follow-up

`tv fundamentals`, `snapshot`, and `compare` already expose scanner-backed
fundamentals and event-like fields. Further work should be small and
evidence-backed:

- improve docs around earnings and dividend fields if downstream users
  misread them;
- add fields only when scanner metainfo evidence and workflow need are clear;
- keep standalone `tv events` deferred unless a complete event/calendar source
  boundary is established.

## Lane 5: Deferred Infrastructure

The following remain out of scope for `v0.10.0` unless a separate plan changes
the boundary:

- `tv diagnose`;
- `tvb`, `tvd`, or other alternate binaries;
- MCP server work;
- daemon, dashboard, or trading-bot behavior;
- cookie/session import or export;
- raw TradingView endpoint primitives;
- public-stable crates.io publication promises.

## Current ExecPlan

- `docs/plans/tradingview-cli-compare-workflow-decision-table.md`

The current polish slice turns the `quotes` / `compare` / `snapshot` /
chart-observation split into a small workflow decision table for docs and
runtime skills. It does not change CLI behavior or the `compare` JSON
contract.
