# v0.20.0 roadmap draft

This document records the `v0.20.0` direction after the `v0.19.0` release.

Status as of 2026-05-26: `v0.19.0` is treated as released. Daily
`tv bars` date-range historical readback is available as the Desktop-free
source for reproducible historical sample preparation. The next useful step
is to mature that same surface for weekly and monthly range reads without
adding a new source or hidden fallback.

After the weekly/monthly range work, pre-release audit, and user onboarding
docs polish completed, `v0.20.0` is in release readiness. No further feature
or refactor work is planned for this release slice.

Post-release note: `v0.20.0` is treated as released. The next roadmap is
`docs/v0.21-roadmap.md`, which groups large-range batching / pagination and
intraday date-range readiness under the same historical bars range maturity
theme.

## Theme

`v0.20.0` is about historical bars range maturity and workflow completeness.

The goal is not to add realtime feeds, watch loops, chart-backed compare,
source mixing, ranking, or trading recommendations. The goal is to make
`tv bars --from --to` more useful for older source-guided examples and
medium-term chart reviews by extending the same `bars.v1` Desktop-free
contract beyond daily bars where the existing protocol can support it safely.

The important boundary remains unchanged: `tv bars` is the historical bars
source. `tv range` moves a selected Desktop chart viewport, and `tv ohlcv`
reads selected-chart bars. Those selected-chart commands are useful for chart
inspection, but they are not hidden fallbacks for reproducible historical
sample preparation.

## Lane 1: Weekly and monthly date-range readback

Status: complete for `v0.20.0`.

Daily range reads made old source-guided examples reproducible for daily
bars. Weekly and monthly bars are the next natural extension because older
VCP, cup-with-handle, and base-pattern examples often need both daily detail
and higher-timeframe context.

The first implementation candidate should support:

- `tv bars <EXCHANGE:SYMBOL> --timeframe 1W --from YYYY-MM-DD --to YYYY-MM-DD`;
- `tv bars <EXCHANGE:SYMBOL> --timeframe 1M --from YYYY-MM-DD --to YYYY-MM-DD`;
- the existing `bars.v1` source metadata, Desktop-free behavior, and
  non-mutating semantics;
- inclusive calendar-date `--from` and `--to` input;
- unchanged count-only mode for recent bounded bars.

Weekly and monthly range reads should not use `tv range`, Replay, screenshots,
selected-chart state, observe/stream JSONL events, scanner quote, chart quote,
or quote-data as hidden source paths.

## Lane 2: Date-range coverage semantics polish

Status: complete for `v0.20.0`.

Daily bars can be checked against calendar dates in a relatively direct way.
Weekly and monthly bars need slightly more careful wording because each bar's
timestamp typically represents the start of a weekly or monthly period. The
contract should make clear that coverage is a source-readback statement about
which bars corresponding to the requested calendar range were returned, not a
claim about pattern quality or trading suitability.

The first slice should use `timestamp_within_requested_range` as the range
filter policy: a returned bar belongs to the date range when the bar timestamp
is inside the requested inclusive calendar range. This is simpler and more
reproducible than trying to infer whether an entire weekly or monthly period
intersects the requested range. The tradeoff is that a weekly or monthly bar
whose period overlaps the first requested days can be omitted when its
timestamp falls before `--from`; docs and payload readback should make that
clear.

The existing additive fields remain the first-pass readback:
`request_mode`, `requested_range`, `returned_range`, `observed_range`, and
`range_coverage_status`. Add `range_alignment` as an additive readback with
the requested timeframe, `bar_timestamp_semantics: "period_start"`,
`range_filter_policy: "timestamp_within_requested_range"`, and
`requested_range_interpretation: "inclusive_calendar_dates"`. Keep `bars[]` as
the raw evidence.

Structured failures should carry the same source and range readback whenever
possible: `contract_version`, requested symbol/timeframe, `request_mode`,
`requested_range`, `range_alignment`, source metadata, `source_availability`,
`wait_summary`, and a follow-up hint. No-bars, timeout, protocol error, and
unsupported timeframe outcomes are source diagnostics, not setup-quality or
trading judgments.

## Lane 3: Source-guided sample workflow completeness

Status: complete for `v0.20.0`.

Docs and runtime skills should teach a clear workflow:

- use `tv bars --from --to` for reproducible Desktop-free historical bars;
- use daily bars for detailed historical pattern work;
- use weekly/monthly bars for higher-timeframe context when supported;
- treat `range_coverage_status` as the primary date-range coverage readback,
  even when count-oriented `summary.coverage_status` or
  `data_quality.partial_result` needs separate interpretation;
- use `tv range` only to move the visible Desktop chart viewport;
- use `tv ohlcv` only when selected-chart CDP bars are the intended source;
- keep scanner quote, chart quote, quote-data, observe/stream, and bars
  evidence separate.

This lane exists because downstream operators need reproducible bars input,
not a visually moved chart whose selected-chart export may still return a
different window.

## Lane 4: Deferred and later candidates

The following remain deferred unless a separate plan changes the boundary:

- intraday date-range reads;
- large-range batching or pagination beyond the bounded `--count` safety cap;
- `tv range` plus `tv ohlcv` automatic historical export;
- Replay-based extraction;
- realtime multi-symbol feed;
- watch or JSONL compare;
- chart-backed compare;
- quote-data auto fallback;
- automatic source mixing;
- standalone `tv events`;
- binary split;
- MCP server work;
- daemon, dashboard, or trading-bot behavior;
- ranking, scoring, or buy/sell recommendations.

Intraday range reads are still valuable, but they are more likely to depend on
retention and entitlement behavior. They should follow weekly/monthly range
maturity rather than being mixed into the first `v0.20.0` slice.
