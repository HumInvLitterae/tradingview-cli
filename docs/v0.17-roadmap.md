# v0.17.0 roadmap draft

This document records the `v0.17.0` direction after the `v0.16.0` release.

Status as of 2026-05-16: `v0.17.0` has been released. Follow-up planning has
moved to `docs/v0.18-roadmap.md`.

## Theme

`v0.17.0` is about historical bars evidence maturity and source workflow
clarity.

The goal is not to add realtime feeds, watch loops, source mixing, or trading
recommendations. The goal is to make stable browserless `tv bars` easier for
agents and downstream tools to use safely: the payload should make the
requested-vs-returned count, time range, ordering, and partial coverage easy
to read before consumers inspect raw `bars[]`.

## Lane 1: `tv bars` evidence maturity

Status: complete for `v0.17.0`.

`tv bars` now returns stable source metadata, raw bars, and additive summary /
range readback for downstream first-pass parsing:

- keep `contract_version: "bars.v1"`;
- keep `source: "tradingview_bars_ws"`;
- keep raw `bars[]` as the detailed evidence;
- expose summary fields for requested count, returned count, first/last time,
  ordering, count fulfillment, and coverage status;
- expose range readback for timeframe, first time, last time, and bar count.

This is historical evidence readback. It is not a ranking, scoring,
recommendation, or trading-action signal.

## Lane 2: Bars availability and failure clarity

Status: complete for `v0.17.0`.

No-bars, timeout, WebSocket error, and partial completion should remain
source-availability readbacks. A failed or partial historical bars request
means the bounded browserless source did not return the requested evidence in
the requested window. It does not mean the symbol has no price, no history, or
no tradable market.

Failure details should stay public-safe and include source metadata,
requested symbol, timeframe, count, and bounded wait / completion summaries.
They should not expose raw WebSocket frames, raw payloads, account-local
metadata, credentials, target ids, or local validation paths.

`tv bars` now treats this as additive `bars.v1` diagnostics: successful
payloads and structured failures should expose `source_availability` with a
public-safe `wait_summary`. No-bars remains a failure, while partial success
with returned bars remains usable historical evidence.

## Lane 3: Source choice workflow clarity

Status: complete for `v0.17.0`.

Historical bars workflows should remain source-aware:

- `tv bars` is Desktop-free, symbol-targeted, bounded historical OHLCV;
- `tv ohlcv` is selected-chart CDP bars;
- scanner-backed `tv quote` / `tv quotes` are Desktop-free quote reads that
  can be delayed;
- `quote-data` is explicit Desktop-backed WebSocket quote-data readback;
- `tv stream ...` commands are Desktop-backed short-window observation
  helpers, not browserless historical bars.

Docs and runtime skills should guide agents to read `summary` / `range`
before using raw `bars[]`, while keeping source boundaries separate.

## Lane 3a: Bars crate-boundary cleanup

Status: complete for `v0.17.0`.

Before release readiness, `tv bars` was aligned with the repository's crate
boundary: Desktop-free historical bars implementation now belongs in
`tradingview-market`, while CLI `ops` remains a thin command adapter. This is a
behavior-preserving refactor and must not change the `bars.v1` payload,
validation, source availability semantics, or command help.

## Lane 3b: Bars market internal split

Status: complete for `v0.17.0`.

After the crate-boundary cleanup, the browserless bars implementation was
split inside `tradingview-market` so the public `bars_symbol` entrypoint stays
small. Validation, TradingView protocol parsing, WebSocket transport, payload
construction, and shared internal types now live in private same-named
submodules under `crates/market/src/bars/`.

This is a behavior-preserving cleanup. It does not change the `bars.v1`
payload, validation shape, source availability semantics, command help, or
public Rust API.

## Lane 3c: CLI contract test organization

Status: complete for `v0.17.0`.

The oversized CLI contract integration test was split into command-family
targets with shared helpers. Root CLI behavior remains in `cli_contract`,
browserless bars in `cli_contract_bars`, Desktop-free market evidence in
`cli_contract_quote`, quote-data diagnostics in `cli_contract_diagnose`, and
CDP-backed command contracts in `cli_contract_desktop`.

This is a test-only cleanup. It does not change CLI behavior, help text,
payload contracts, validation semantics, dependencies, or versioning.

## Lane 4: Deferred and later candidates

The following remain deferred unless a separate plan changes the boundary:

- realtime multi-symbol feed;
- watch or JSONL compare;
- chart-backed compare;
- quote-data auto fallback;
- automatic source mixing;
- standalone `tv events`;
- binary split;
- MCP server work;
- daemon, dashboard, or trading-bot behavior;
- ranking, scoring, or buy/sell recommendations.

## Current Plan

- `docs/v0.18-roadmap.md`
- `docs/plans/tradingview-cli-jsonl-observation-contract.md`

The next roadmap focuses on existing Desktop-backed JSONL observation
contracts for `tv observe chart` and `tv stream ...`. It does not add
realtime multi-symbol feeds, source mixing, chart-backed compare, automatic
fallback, or new market-data sources.
