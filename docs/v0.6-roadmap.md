# v0.6.0 roadmap draft

This document records the `v0.6.0` direction after the `v0.5.0` release.

Status as of 2026-05-05: `v0.5.1` has been released, roadmap and command
source taxonomy work is recorded, and the first `v0.6.0` implementation slices
added stream observation controls, stream source metadata, `tv readiness`, and
screenshot visual-evidence metadata. The current follow-up aligns core
Desktop-backed read payloads with the command source taxonomy. The `tv` binary
remains a single command.

## Goal

`v0.6.0` should move `tv` toward an observation-first TradingView agent
toolkit. The CLI should keep producing structured reads and newline-delimited
JSON observations that downstream agents can consume, while avoiding hidden
state changes and broad trading-bot behavior.

The preferred direction is:

1. keep one `tv` binary for now and classify commands by source instead of
   splitting into Desktop-free and Desktop-backed executables;
2. strengthen pull-based observation, where `tv` emits bounded JSON or JSONL
   events and an external agent decides what to do next;
3. improve Desktop-backed readiness and recovery where TradingView Desktop is
   the source of truth;
4. keep experimental browserless data paths lab-gated until protocol stability
   and downstream value are clearer.

## Lane 0: Patch Candidate Before v0.6.0

`tv quote <SYMBOL> --source chart` had one reported symbol/data mismatch after
the `v0.5.0` release. That trust issue is handled as the focused `v0.5.1`
patch release rather than waiting for the broader `v0.6.0` roadmap.

The patch hardens chart-source quote success conditions by comparing requested
symbol, observed quote symbol, current chart symbol, bar signature, and bar
availability, then requiring consecutive stable readiness before returning
success. If the CLI cannot prove the data belongs to the requested symbol, it
returns a structured readiness error instead of relying on downstream sleep or
double-call workarounds.

The patch also has an opt-in ignored Rust integration smoke for maintainers who
want to run a live Desktop sequence before release. It is intentionally not part
of CI because it depends on a running TradingView Desktop target.

## Lane 1: Desktop-free Observation And Market Reads

Current Desktop-free reads include `tv info <SYMBOL>`,
`tv fundamentals <SYMBOL>`, `tv quote <SYMBOL>`, `tv quotes <SYMBOL>...`,
`tv scanner scan`, `tv scanner hotlist`, and `tv scanner metainfo`.
`tv bars` is an experimental browserless historical-bars prototype gated by
`TV_EXPERIMENTAL_BARS=1`.

Good `v0.6.0` candidates:

- add bounded observation controls to the existing Desktop-backed
  `tv stream ...` JSONL contract;
- design browserless observation candidates such as quote or bar streams
  without adding authenticated cookie/session import;
- add bounded controls such as duration, max events, heartbeat, and explicit
  freshness metadata where current stream or observe workflows need them;
- continue treating `tv bars` as lab-only until evidence justifies
  stabilization or movement into a reusable read crate.

Not good default candidates:

- daemon, MCP server, dashboard, or trading-bot behavior;
- unbounded streams without explicit stop conditions;
- authenticated direct HTTP, cookie/session export, or login automation.

## Lane 2: Desktop-backed Readiness And Recovery

TradingView Desktop remains the source of truth for selected chart state,
visible UI, screenshots, Pine Editor state, Replay state, and account-backed
operations.

Good `v0.6.0` candidates:

- add `tv readiness` as a narrow, non-mutating wrapper over target discovery,
  chart state, OHLCV bar readiness, and screenshot hints;
- add source taxonomy and file-write metadata to `tv screenshot` so visual
  evidence can be distinguished from chart API reads and market data reads;
- add source taxonomy metadata to core Desktop-backed reads such as `status`,
  `tab list`, `state`, `ohlcv`, and chart-source quote;
- keep broad `tv diagnose` deferred until `readiness` usage shows what extra
  troubleshooting context is still missing;
- improve recovery guidance for chart target confusion, full-page Screener
  target setup, and chart-bars readiness failures;
- keep Computer Use as a Codex app-only visual recovery aid, used after
  structured CLI diagnostics and portable screenshots.

Not good default candidates:

- generic UI automation expansion;
- broad new account mutations;
- retries that hide readiness problems instead of reporting structured
  diagnostics.

## Lane 3: Command Source Taxonomy And UX Clarity

The single `tv` binary now needs clearer source labeling rather than binary
splitting. The durable taxonomy lives in `docs/command-source-taxonomy.md`.

The categories are:

- `Desktop-free read`;
- `Desktop-backed read`;
- `Desktop-backed operation`;
- `Hybrid`;
- `Experimental`.

Good `v0.6.0` candidates:

- keep README, help text, docs, and runtime skills aligned with these
  categories;
- audit JSON payloads for consistent `source`, `non_mutating`, `experimental`,
  and freshness metadata where those fields already exist or can be added
  without breaking compatibility;
- revisit a future binary split only after downstream use shows that separate
  executables would reduce confusion more than they increase operational
  friction.

Deferred by default:

- `tvb`, `tvd`, or other alternate binaries;
- changing default command behavior just to match the taxonomy;
- removing hybrid command support before source-specific workflows are stable.

## Current ExecPlan

- `docs/plans/tradingview-cli-core-read-source-metadata.md`

This slice adds additive source taxonomy metadata to core Desktop-backed read
success payloads. It does not add new command surface, change fallback behavior,
or change Desktop-free scanner quote payloads.

## Deferred by default

- MCP server work;
- trading bots, dashboards, or workflow packs;
- raw TradingView endpoint primitives;
- cookie/session import or export;
- broad non-numeric Screener filter editing;
- generic UI automation beyond compatibility needs;
- public-stable crates.io publication promises.
