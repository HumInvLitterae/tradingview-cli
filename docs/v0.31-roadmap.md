# v0.31.0 roadmap

This document records the direction after the `v0.30.2` release.

Status as of 2026-07-27: `v0.30.2` is released from commit `e8e480d`. The
ordered inventory is `docs/v0.31-work-items.md`. One-minute Desktop-free bars
date-range harness corrections, focused non-live validation, and narrow
re-review are green. After an initial transient connection failure, bounded
production-binary comparison confirmed the common five-minute path and all
three intended one-minute scenarios. Focused closeout review is the current
gate. No version bump or release operation is authorized by this roadmap alone.

## Theme

`v0.31.0` focuses on historical bar completeness and reproducible downstream
inputs.

The first goal closes a concrete downstream gap: bounded `tv bars` date-range
mode now supports `1` and its `1m` alias alongside `5`, `15`, `30`, `60`,
`1D`, `1W`, and `1M`. Downstream preparation had verified complete private
5-minute and 15-minute corpora but could not request the required one-minute
series through the same `bars.v1` date-range contract before this change.

The supplied downstream report also describes separate historical basket
preparation. That is context, not a requested CLI deliverable, and it does not
create a v0.31 work item.

## One-minute bars date ranges

Priority: highest. Status: second harness correction, focused non-live
validation, and narrow re-review green. Bounded production-binary comparison
confirmed single-window, additional-window, and closure-boundary behavior;
focused closeout review pending.

Extend only `tv bars <SYMBOL> --timeframe 1 --from YYYY-MM-DD --to YYYY-MM-DD`.
The `1m` alias already normalizes to `1` and should follow the same path. Keep
the source as `tradingview_bars_ws` and the contract version as `bars.v1`.

Preserve the existing date-range contract:

- inclusive calendar-date input and half-open timestamp filtering;
- `range_alignment.bar_timestamp_semantics: "period_start"`;
- `requested_range`, `returned_range`, `observed_range`,
  `range_coverage_status`, `range_fetch_summary`, and source availability;
- a returned-bar safety cap of 5,000;
- 500-bar fetch windows, one existing absolute request deadline, and no retry;
- explicit `range_truncated` and `range_truncation_reason` when coverage is
  incomplete because of count cap, timeout, or source exhaustion.

Do not widen every guarded intraday timeframe in this slice. Timeframes `3`,
`45`, `120`, `180`, and `240` remain date-range validation errors until a
separate workload demonstrates need. Count-only behavior remains unchanged.

The implementation must not treat market closures as missing bars by guessing
an exchange calendar. Weekend, holiday, halt, and entitlement cases retain the
existing conservative source and coverage vocabulary. No synthetic bars or
silent completeness claim may be introduced.

Active ExecPlan:
`docs/plans/tradingview-cli-one-minute-bars-date-range.md`.

## Downstream integration boundary

Priority: immediately after the one-minute slice. Status: documentation and
contract handoff only.

After implementation evidence is reviewed, record the exact stable invocation
and fields downstream should consume. A downstream workflow may split a larger
historical interval into multiple requests because the 5,000 returned-bar cap
is intentionally preserved. Cross-request merging, package sealing, private
case selection, and receipt generation remain downstream responsibilities.

Do not write private symbols, prices, case dates, basket membership, or
authority digests into this repository. Public tests use fixed synthetic bars
or public-safe fixtures only.

Priority: conditional after one-minute bars closeout.

Re-evaluate at most one user-facing candidate after the downstream blocker is
closed:

| --- | --- | --- |

bounded behavior, public-safe evidence, and an independent ExecPlan. A

## Evidence-triggered engineering candidates

These are not ordered v0.31 implementation tasks. Reopen them only when their
existing trigger is observed:

| Candidate | Re-evaluation trigger |
| --- | --- |
| Pre-dispatch retry or stale-endpoint refresh | Ordinary `target_list` or `websocket_connect` failure, or a later bounded probe that reproduces one. |
| Chart-read subprocess attribution | A chart read above one second, a timeout, or a `method_call` failure stage. |
| Shared session or broker | New stale-event or renderer-lifecycle evidence plus an explicit background-service policy decision; latency alone is insufficient. |
| Public recovery metadata | Shared boundaries can derive dispatch/effect state safely and a consumer needs distinct machine actions. |
| Generalized waits or input preconditions | A named operation demonstrates a repeated, bounded readiness failure. |
| Explicit-target `status` listing optimization | Before/after evidence shows material cost without weakening freshness or failure attribution. |
| Renderer lifecycle and indicator search | A concrete render-linked transition mechanism or relevant Desktop build change; HTTP activation and `Page.bringToFront` are current-build no-go. |

Other preserved feasibility candidates are finite-`f64` right-offset
restoration, width-derived drawing geometry, and Windows MSIX/AUMID launch
activation. None has a current v0.31 trigger.

## Maintained exclusions

Automatic foreground behavior and production indicator search remain
unapproved unless the renderer-lifecycle trigger above is met.
Method-post-dispatch restart, MCP, daemon operation, binary splitting,
cookie/session import, login automation, trading bots, automatic source
mixing, ranking, scoring, recommendation, and trading actions remain excluded.

The 5,000-bar safety cap is not raised in the one-minute slice. A larger single
request or new pagination contract requires separate scale evidence and must
not be smuggled into timeframe validation.
