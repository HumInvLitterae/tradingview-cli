`v0.39.0` strengthens Desktop alert-creation confirmation. Indicator alerts are
attributed to the creation response ID and checked against the submitted
settings. Price-alert errors preserve uncertainty after a possible account write.

## Confirm indicator creation

Normal `alert create-indicator` calls now require the saved row to match the
creation response ID and the submitted condition, saved script revision, inputs,
symbol settings, resolution, message, notifications and expiry. This prevents an
unrelated concurrent alert with matching content from confirming the request.
The rule applies both with and without opt-in preflight verification.

Successful results add these fields:

```json
{
  "created": true,
  "confirmation": {"identity": "matched", "settings": "matched"},
  "activation": {"state": "active"}
}
```

Activation can be `active`, `pending` or `unknown`. A pending result means the
saved row is inactive with explicitly empty stop/error fields; it does not
promise eventual activation. Unknown means activation data is incomplete or
contradictory. Neither state triggers automatic waiting, retry or reactivation.
Confirmation of saved settings does not establish notification delivery.

An attributable alert whose settings cannot be confirmed, do not match, or show
a stopped state returns an error with `created:true` and its alert ID. The
reasons are `settings_unavailable`, `settings_mismatch` or `activation_stopped`.
Consumers must distinguish that confirmed creation from an uncertain result:
`created:null` with `creation_outcome:"unknown"`. Neither is permission to repeat
the create request blindly. Proven preflight failures retain `created:false`.

CLI arguments, Rust operation signatures, notification defaults, dry-run behavior
and existing preflight verification fields are unchanged. Official MCP operations
are unchanged. Public alert listing does not expose the full private Pine inputs
used by the internal comparison.

## Preserve uncertain price-alert outcomes

Desktop `alert create` errors after a possible write now report `created:null`
and `creation_outcome:"unknown"`, including lost responses and failed readback.
They no longer imply that no alert was created. Proven preflight failures retain
`created:false`. Successful output, error kinds, exit codes and retry behavior
are unchanged. Price-alert response-ID attribution is not included in this release.

## Dependencies

Tokio advances from 1.53.2 to 1.53.3, with twelve compatible transitive updates,
including Rustls and platform certificate/IPC support. MCP mutation/readback
fixture deadlines were stabilized without changing product timeouts.

Saved-settings confirmation is distinct from notification delivery. The public
list projection does not expose private Pine inputs, and price-alert response-ID
attribution remains outside this release. Cross-platform release checks and
archive contents follow the [release packaging contract](../release-packaging.md).
