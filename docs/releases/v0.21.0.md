This release makes `tv bars <EXCHANGE:SYMBOL>` more useful for reproducible
historical sample preparation across larger date ranges and selected intraday
timeframes. It keeps the existing Desktop-free `bars.v1` source boundary and
does not add selected-chart export, Replay extraction, source mixing, ranking,
or recommendations.

## Highlights

- Added `range_fetch_summary` to date-range `tv bars` payloads and structured
  failure details so agents and downstream tools can read bounded fetch
  windows, `request_more_data` attempts, observed / filtered / returned
  counts, count caps, and truncation reasons.
- Raised the date-range `--count` safety cap from 500 to 5000 for supported
  `tv bars --from --to` reads. Recent count mode remains capped at 500.
- Added narrow intraday date-range support for `5`, `15`, `30`, and `60`
  timeframes alongside `1D`, `1W`, and `1M`.
- Kept `1`, `3`, `45`, `120`, `180`, and `240` date-range requests guarded by
  validation before network access.

## Behavior Notes

- `tv bars --from --to` supports date-range mode for `5`, `15`, `30`, `60`,
  `1D`, `1W`, and `1M`.
- In date-range mode, `--count` is a returned-bar safety cap. It defaults to
  500 and may be raised up to 5000.
- `range_coverage_status` remains the primary coverage readback for the
  requested date range. Read `range_fetch_summary` to understand fetch windows,
  count-cap truncation, timeout, or source exhaustion.
- `range_alignment` still explains period-start bar timestamps and the
  `timestamp_within_requested_range` filter policy.
- `tv bars` remains separate from `tv range`, `tv ohlcv`, Replay, observe /
  stream, scanner quote, chart quote, and quote-data. It does not rank, score,
  recommend, trade, or mix sources.

## Packaging
